# OmniFlow 白皮书

---

# 第一部分：愿景与理论基础

---

## 1. 产品定义

### 1.1 什么是 OmniFlow

OmniFlow 是一套面向硬核自动化游戏的**可视化产线矩阵求解器**。它将运筹学中的单纯形矩阵求解（Linear Programming）与工业控制台的节点图范式（Node Graph）融合，提供所见即所得、跨模组通用、数学驱动的工业生产排程引擎。

核心公式概括为一行：

> **React Flow 节点编辑器 + SciPy 线性规划 = 确定性全局最优产线配置**

OmniFlow 不绑定任何特定游戏——其底层不包含任何硬编码的游戏逻辑。切换模组环境仅需更换资源配置文件，核心求解管线无需一行代码改动。

---

### 1.2 目标用户与对标系统

**目标用户**：格雷科技（GregTech）、机械动力（Create）、异星工厂（Factorio）等硬核自动化游戏的深度玩家，以及需要批量仿真产线配置的整合包作者。

**现有工具的局限**：

| 痛点 | 说明 |
|------|------|
| **硬编码耦合** | 现有计算器深度绑定特定模组版本，无法适配自定义整合包或多游戏场景 |
| **语境歧义** | 同一资源（如水）既是配方原料又是机器冷却液，传统单维数据模型无法表达这种正交关系 |
| **非线性发散** | 手工枚举或迭代逼近在面对超频级联、概率副产、全局管网共享等多目标耦合时，要么发散，要么精度不可接受 |

OmniFlow 以矩阵求解替代手工枚举，以节点图编辑器替代电子表格，从根本上解决了上述三个困境。

---

### 1.3 核心设计原则

**原则一：数学优先（Math-First）。** 前端负责全部业务逻辑（归一化、修饰器管线、拓扑编译），将所有离散量与连续量统一降维为纯净的每秒速率（Rate/s）。后端仅接收标准形式的线性规划问题，在 30ms 内返回最优解。

**原则二：本体解耦（Ontological Decoupling）。** 物质的物理身份（是什么）与使用语境（怎么用）彻底分离。全局字典定义一次物质本质，具体角色由机器底盘与配方插槽在节点层赋予。

**原则三：沉默即默认（Silent Default）。** 系统只显式声明"不守规矩"的特例。99% 的资产无需一行配置即可正确运转。

**原则四：管线不可逆（Irreversible Pipeline）。** 数据从定义到求解经历严格四阶段流转：隔离 → 降维 → 拆分 → 拍平。越级操作严禁。

## 2. 工业资源本体论

### 2.1 本体论问题：同一物质，双重身份

在自动化游戏的产线计算器领域，一个重要的架构问题长期被忽视：**如果我们在底层将"机器槽位的资源"与"配方所需的资源"割裂为两套独立系统，最终必然导致逻辑矛盾。**

举例而言——水既可作为电解配方中的反应原料参与化学转化，同时又可作为机器底盘的冷却液维持设备运转。同一物质、同一标识符、两种截然不同的因果身份。

从现实工业排程（ERP）与游戏引擎 ECS 架构的角度审视，结论是明确的：

> **所有资源本质上位于同一个资源池中。决定它们行为差异的，不是资源本身，而是它们被接入的接口（Socket）。**

基于此，OmniFlow 提出了一套普适的 **工业资源宏观分类矩阵**，以两个正交维度对所有工业资源进行系统分类。

---

### 2.2 维度一：物理与数学性质（The Nature Dimension）

此维度不关心资源为谁所用，只关心资源在矩阵方程中呈现何种数学形态。所有实体严格归入以下三类：

---

#### 2.2.1 累积量 / 流量型（Volumetric / Consumable）

- **本质特征**：以离散数量计量（以 pcs、L 为单位），消耗即减少，允许囤积于箱子、储罐等容器中。
- **数学抽象**：以单次生产周期为基准，稳态通量定义为：

$$
\text{Rate} = \frac{\text{Amount}}{\text{Duration}}
$$

- **典型实例**：铁矿石、水、原油、机器维护保养所需的备件。

此类实体是物料平衡方程的输入输出项，也是化学计量矩阵系数的直接来源。

---

#### 2.2.2 连续率 / 驱动型（Continuous Rate / Driving Force）

- **本质特征**：以连续能量流形式存在（以 J/t、N·m 为表征），不可囤积、不可停滞——一旦断开则关联机器立即停机。
- **数学抽象**：其表征本身即为速率量纲，无需额外转换。在并行扩展场景中表现为线性缩放，在超频加压场景中则呈现非线性突变。
- **典型实例**：电力（EU/t）、机械应力（SU）、热功率（HU/t）、激光能。

此类实体作为线性规划的约束边界出现——总消耗不得超过总供给，总产出不得低于总需求。其"用即分配、断即停产"的特性，使其成为产线中最敏感的瓶颈因子。

---

#### 2.2.3 状态 / 阈值型（State / Threshold）

- **本质特征**：作为"环境门槛"或"启动判据"存在，不被消耗，也不作为动力。满足则运行，不满足则停机。
- **数学抽象**：核心数学性质为：

$$
\textbf{稳态物质通量} \equiv 0
$$

状态/阈值型约束的消解在**前端编译阶段**完成，不进入后端 LP 矩阵。当前版本采用纯连续线性规划，未来若引入变量离散选择（如"求解器决定能源仓等级"）才会开启 MILP 路径。三步消解规则见第 8.5.1 节。

- **典型实例**：机器温度 $\gt 1000\text{K}$、必须处于"末地"维度、必须拥有"群系：海洋"标签、必须满足 3 级以上无尘室环境。

这类实体是配方可否执行的"资格鉴定器"——它们不消耗、不产出、不流转，但可决定一条产线是否具备运行资格。

---

### 2.3 维度二：绑定上下文（The Context Dimension）

资源本身没有"底盘 / 配方"之分，是**节点上的插槽（Port）**赋予了它们身份。OmniFlow 将节点的输入/输出接口分为两个互不重叠的语义区：

---

#### 2.3.1 基建插槽（Infrastructure Port / Chassis Bound）

- **因果关系**：为维持机器本身的运转而存在，与配方选择无关。无论加工何种原料，单次运行的基础耗电量恒定。**但需注意：当并行执行多份配方时，基建消耗（包括电力）会等比例放大——并行意味着更高的能源消耗。**
- **数据来源**：由机器的"底盘原型（Archetype）"锁定声明，全局统一。

---

#### 2.3.2 加工插槽（Payload Port / Recipe Bound）

- **因果关系**：为实现某一次物质转换而存在。
- **数据来源**：由"配方（Recipe）"声明。配方更换，插槽内容随之更换。

---

两者的区分看似简单，实则从根本上解决了"同一资源双重身份"的建模冲突。基建插槽与加工插槽可以同时引用字典中同一个 `water` 条目，各自声明独立的数量和速率，互不干扰。

---

### 2.4 催化剂与工具：跨界形态

催化剂/工具型资源是工业排程建模中的关键难点，也是多数计算器在处理编程电路板、挤压模具、透镜等物品时容易出错的环节。

在 OmniFlow 的分类体系中，**催化剂/工具并非一种全新的资源类型，而是介于"累积量"与"阈值型"之间的特殊形态。** 根据其物理行为，须拆分为两种子类型分别处理：

---

#### 2.4.1 绝对不消耗型（编程电路板、模具、透镜）

- **物理本质**：状态 / 阈值型约束。本质上是一把"钥匙"——持有即解锁，不参与任何物料流转。
- **稳态处理**：消耗速率恒为零。后端 SciPy 引擎不应知晓其存在。
- **UI 表现**：前端在 Inputs 列表中照常渲染，但速率显示为灰色的 $0\text{/s}$，并附带非消耗标记。
- **编译行为**：前端在组装后端 Payload 时，一旦识别 $\texttt{consumable: false}$，直接将其剔除出矩阵。它属于建厂的**初始成本（CapEx）**，而非**运营成本（OpEx）**。

---

#### 2.4.2 带耐久 / 概率消耗型（锤子、扳手、降解催化剂）

- **物理本质**：累积量 / 流量型资源。消耗速度极慢，且通常掺杂随机性。
- **数学处理**：将耐久损伤或损耗概率转化为数学期望值（Expected Value）。

> 示例：配方每次消耗 $10$ 点锤子耐久，锤子总耐久 $10000$。
> 换算：每次循环消耗 $\displaystyle\frac{10}{10000} = 0.001$ 把锤子。
> 实际速率：0.001 / Duration。

- **架构影响**：字典中仍为普通 $\texttt{item}$，但配方定义中 $\texttt{amount}$ 允许浮点数。矩阵收到极小速率后，可精确计算每小时需自动补充多少把锤子。

---

#### 2.4.3 数据层落实

为兼容上述两种情形，无需改动全局字典，仅需在配方的输入定义中增加属性标记：

| 属性 | 语义 | 矩阵行为 |
|------|------|----------|
| `consumable: false` | 绝对不消耗（阈值型钥匙） | 剔除，不计入稳态计算 |
| `probability: <float>` | 概率消耗（期望值转换） | $\text{effective_amount} = \text{amount} \times \text{probability}$ |

---

## 3. 命名体系：原型继承与级联覆盖

前两章确立了"资源是什么"的分类体系，本章解决"资源如何被系统识别与解析"。OmniFlow 采用 **原型继承与级联覆盖（Prototype Inheritance & Cascading Override）** 模式，以量纲（Dimension）为基础，以资源特化（Override）为扩展，构建一套维护成本极低的数据驱动引擎。

---

### 3.1 量纲与单位的分离

在严谨的工程与物理计算中：

> **量纲（Dimension）** 决定了物质的数学本质——这是体积？是质量？还是能量？
> **单位（Unit）** 仅仅是量纲在不同模组语境下的具体表象——mB、EU、RF 均是对同一量纲在不同模组中的特定翻译。

将两者解耦，意味着系统在底层只认量纲（用于数学约束的正确性），在表层才翻译为单位（用于 UI 的可读性）。物理意义与展示逻辑就此彻底隔离。

---

### 3.2 极度克制的双注册表

在这套模式中，资源注册表 **不需要** 将上万种物品全部录入。仅"不守规矩"的特例才需要显式声明。

**量纲注册表（Dimension Registry）**——定义物理世界的底层法则：

| 量纲 | 默认单位 | 显示模式 | 说明 |
|------|----------|----------|------|
| `item` | pcs | rate_per_sec | 离散物品 |
| `fluid` | L | rate_per_sec | 流体 |
| `energy` | J | rate_per_tick | 通用能量 |
| `stress` | N·m | rate_per_sec | 机械应力 |
| `heat` | K | rate_per_tick | 热能 |

**资源注册表（Resource Registry）**——仅记录特化覆盖（示例）：

| 资产 ID | 继承量纲 | 覆盖单位 |
|---------|----------|----------|
| `mod_power` | `energy` | `EU` |
| `rf_power` | `energy` | `RF` |
| `mech_power` | `stress` | `RPM` |

所有未在此表中出现的资产沿量纲默认设置自动运行。`iron_ingot` 一行都不需要写——它自动归入 `item` 量纲，单位 `pcs`。

此设计的核心价值在于 **沉默即默认**：系统中 99% 的物品无需一行声明即可正确运转。

---

### 3.3 三级解析管线

当解析器接收到一个完整的资产 ID（形如 `dimension:asset_id`，例如 `item:iron_ingot` 或 `energy:mod_power`）时，查询逻辑遵循严格的级联回退链：

| 查找层级 | 来源 | 优先级 | 示例 |
|----------|------|--------|------|
| **Tier 1** | `ResourceRegistry[assetId]` 显式覆盖 | 最高 | `mod_power` → 单位覆写为 `EU` |
| **Tier 2** | `DimensionRegistry[dimensionId]` 量纲默认 | 中 | 所有 `item:*` → 单位默认 `pcs` |
| **Tier 3** | 硬编码兜底 | 最低 | 未知量纲 → `?`（永不崩溃） |

**这一设计实现的效果**：

**① 天然兼容所有符合命名规范的未知 Mod。** 若玩家安装了一个未适配的模组，其中定义了 `energy:magic_mana` 这样一种 OmniFlow 从未见过的能源，系统三级解析回退至 `DimensionRegistry['energy']`，自动赋上 `J/t` 单位并正确参与矩阵计算。**系统零崩溃，零适配成本。**

**② 物理意义的绝对隔离。** 无论 UI 上显示 EU、RF 还是魔法值，在底层的 Python 线性规划矩阵中，所有能量型变量的约束均严格基于 `energy` 量纲进行降维——不同量纲的约束互不干扰，物理维度始终保持一致。

## 4. 架构总览

### 4.1 端到端数据流全景

OmniFlow 的端到端数据流可以概括为一条跨越前端与后端的单向管线：

```

│         │                  │                              │

└─────────┼──────────────────┼──────────────────────────────┘
          │                  │

┌─────────────────────────────────────────────────────────┐
```

### 4.2 三层架构：字典层 → 节点层 → 引擎层

| 层级 | 职责 | 输入 | 输出 |
|------|------|------|------|
| **字典层（Global Registry）** | 客观描述实体元数据（单位、颜色、量纲） | 无依赖 | 纯实体定义 |
| **节点层（Node Definition）** | 将实体接入具体语境（基建插槽 / 加工插槽） | 字典引用 + 底盘 + 配方 | 语境化的资源列表 |
| **引擎层（Solver）** | 接收归一化向量，求解全局最优 | 拍平后的 Dict[id, rate] | 每节点机器数 & 实际吞吐量 |

三层之间单向依赖，无循环引用。字典不感知节点，节点不感知求解器。

## 5. 资源生命周期：四阶段不可逆流转

一份资源的数字身份，从用户配置到矩阵求解，经历严格四阶段流转，且绝对不允许越级操作。这一设计的核心原则概括为：

> **UI 讲究语义，数学只看正负。**

---

### 5.1 阶段一：定义层（The Blueprint）—— 严格隔离

在 React Flow 的原始节点状态（Raw State）中，资源数据**不得**提前合并。两类输入源必须作为独立数组存储，严格隔离。

| 数据源 | 来源 | 语义 | 示例 |
|--------|------|------|------|
| **配方 IO（Recipe IO）** | 玩家手动填写的配方数据 | "我要把一块铁锭烧成一块钢锭" | `item:iron_ingot` → `amount: 1` |
| **设施 IO（Utility IO）** | 机器底盘 Archetype 的 `fixed_utilities` | "烤炉本身需要通电才能运转" | `energy:mod_power` → `amount: 32`，带 `io_type` |

此阶段的最高原则是 **保持语义纯度**：底盘的归底盘，配方的归配方。任何在这一层做合并的尝试都会污染后续所有环节的可溯源性。

---

### 5.2 阶段二：计算管线（The Physics Engine）—— 统一降维

一旦进入修饰器管线（第 6 章），**语义彻底消失**。修饰器是一个黑盒——它接收两个独立数组（配方 IO + 设施 IO），内部将它们统一对待，执行以下归一化：

> 所有离散的量纲化数字（如 10 秒、256 J/t、8 个物品）被降维为纯净的 **每秒速率（Rate/s）**。

这一步骤至关重要：24000 J（一次配方）和 32 J/t（设施持续消耗）在归一化后处于同一量纲空间，方可进行有物理意义的并行、超频等运算。任何尚未降维为 Rate 的数据不得进入此阶段。

---

### 5.3 阶段三：视图层（The View Model）—— 结构化拆分

管线完成计算后，**语义必须回归**。管线产出的结果必须保持拆分状态，分入四个结构化数组：

| 数组 | 内容 | UI 用途 |
|------|------|---------|
| `recipe_inputs` | 经管线变换后的配方输入（Rate/s） | 节点卡片上半部——加工区 |
| `recipe_outputs` | 经管线变换后的配方输出（Rate/s） | 节点卡片上半部——加工区 |
| `utility_inputs` | 经管线变换后的设施输入（如耗电量） | 节点卡片下半部——基建区 |
| `utility_outputs` | 经管线变换后的设施产出（如废料、排气） | 节点卡片下半部——基建区 |

拆分是视图层的义务：节点卡片 UI 依赖此拆分区分加工区与基建区；SystemHUD 依赖它来遍历各数组，借助 `dimension:asset` 字典查询当前数据是否关联全局管网，做出聚合显示决策。

---

### 5.4 阶段四：传输层（The Matrix Payload）—— 降维拍平

在 `axios` / `fetch` 发起后端请求的最后一刻，执行最终的数据归约：

> 后端求解器不感知域语义。它不区分"配方"与"设施"，不关心"加工"与"基建"。它只处理一个事实——**节点 A 对某个物质 ID 的净消耗/净产出速率是多少。**

因此，传输层在组装 Payload 时，将所有 Input 数组拍平为一个 `Dict[string, number]`，将所有 Output 数组拍平为一个 `Dict[string, number]`。同一物质 ID 的多个来源（配方 + 设施）在此处被求和合并（如冷却水 10 mB/s + 电解水 50 mB/s = 合并为 `water: -60 mB/s`）。

```
┌────────────────────────────────────────────────────────────────────────┐
│  阶段一 (定义层)       阶段二 (管线)      阶段三 (视图)    阶段四 (传输)   │
│                                                                        │
│  Recipe IO ──┐                       recipe_inputs  ──┐                │
│              ├──→ [修饰器管线] →      recipe_outputs   │                │
│  Utility IO ─┘     归一化为 Rate      utility_inputs   ├──→ 拍平 → 后端  │    
│                                     utility_outputs ──┘                │
│                                                                        │
│    语义隔离              语义消失           语义回归         语义作废     │
└────────────────────────────────────────────────────────────────────────┘
```

| 阶段 | 核心操作 | 语义状态 | 禁止事项 |
|------|----------|----------|----------|
| **定义层** | 原始数据分离存储 | 配方 ≠ 设施 | 禁止提前合并 |
| **计算管线** | 归一化为 Rate/s，执行修饰器 | 全量纲消失 | 禁止保留离散单位 |
| **视图层** | 结构化拆分为四数组 | 语义回归 | 禁止在此层做数值变形 |
| **传输层** | 拍平为 `Dict[id, rate]` | 语义作废，只剩正负 | 禁止保留任何 UI 状态 |

## 6. 修饰器引擎：顺序管线

前四章解决了资源如何分类、解析与架构组织，本章聚焦一个关键问题：**配方本身在进入矩阵之前，经历过怎样的变形？**

---

### 6.1 核心哲学：修饰器是工序，不是标签

在传统的 RPG 数值体系或简单的工厂计算器中，修饰器（Modifier）通常被实现为一组静态的乘数因子，然后一次性叠乘到基础数值上。这种方式在纯线性的数值空间里行之有效，代码也极其简洁。

但在《格雷科技》和《机械动力》这类硬核模组面前，上述做法会立即失效。原因在于，这些模组的加工逻辑大量依赖 **阈值判断、限幅钳位、循环探测** 等离散数学与非线性运算。

OmniFlow 因此确立了修饰器引擎的核心规则：

> **修饰器不是一张张静态的数值标签，而是一道道具有独立计算能力的加工工序。**

每一个修饰器都是一个黑盒处理器（Black-Box Processor）。配方对象（Recipe State）依次流经这些黑盒，被逐一变换、缩放、裁剪，最终产出一个经过完整物理仿真后的状态，送入矩阵求解。

---

### 6.2 修饰器与管线上下文

#### 6.2.1 状态对象（PipelineContext）

```typescript
interface PipelineContext {
  recipeInputs:  Resource[]    // 配方输入（加工区）
  recipeOutputs: Resource[]    // 配方输出（加工区）
  utilityInputs: Resource[]    // 设施输入（基建区）
  utilityOutputs: Resource[]   // 设施产出（基建区）
  durationSeconds: number      // 配方单次耗时
  machineStopped: boolean      // 机器是否因不满足条件而停机
}
```

管线从深拷贝的原始配方数据初始化 `PipelineContext`。每一步修饰器的 `evaluate()` 接收的是**当前这一行上面所有工序修改后的 `PipelineContext` 快照**——不是基础配方数据。修饰器直接在 Context 上原地修改，后续工序立即可见。这是修饰器之间唯一的状态通道。

---

#### 6.2.2 执行规则：全序执行，无跳跃、无合并

修饰器的执行严格遵循 `active_modifiers` 数组的索引顺序，逐一施加。没有任何修饰器可以跳过前面的修饰器、合并到其他修饰器、或自行决定执行顺序。

```
active_modifiers = [M1,      M2,      M3,    ...,    Mn]     ← 数组位置 = UI 自上而下
                     │       │        │               │
                     ▼       ▼        ▼               ▼
PipelineContext → [ M1 ] → [ M2 ] → [ M3 ] → ... → [ Mn ] → 归一化 → 矩阵
                   原地修改  原地修改  原地修改        原地修改
```

**数组顺序 = UI 列表自上而下的顺序。** 用户可以在修饰器设置界面拖拽行项目来重排顺序，从而精确控制执行链。同一行就是一个不可再分的工序。

此规则统一适用于所有修饰器——纯线性乘数不享有预折叠特权。乘法器的性能开销在产线级场景下可忽略不计（200 个配方 × 5 个修饰器 = 1000 次乘法，< 1 ms），统一语义和排错便利的价值远高于微秒级优化。

---

#### 6.2.3 管线结构

修饰器链依次处理配方状态，PipelineContext 是唯一的信息传递介质：

```
┌───────────┐     ┌───────────┐     ┌───────────┐     ┌───────────┐     ┌───────────┐     ┌──────────┐
│  原始配方   │ ──→│  修饰器 1  │ ──→│  修饰器 2  │ ──→ │  修饰器 3  │ ──→│  修饰器 4  │ ──→ │  矩阵    │
│  (Raw)    │     │           │     │           │     │           │     │           │     │  引擎      │
└───────────┘     └─────┬─────┘     └─────┬─────┘     └─────┬─────┘     └─────┬─────┘     └──────────┘
                        │                 │                 │                 │
                  modifies:         modifies:         modifies:         modifies:
                  Context fields    Context fields    Context fields    Context fields

                        ▼                 ▼                 ▼                 ▼
                  Context 快照 1     Context 快照 2     Context 快照 3     Context 快照 4
```

每个修饰器的具体行为和数学性质由其自身的 `evaluate()` 实现决定，引擎仅负责按序调用并传递 Context。第 6.5 节给出完整的实例推演。

---

#### 6.2.4 时间缩放与设施消耗的精确规则

超频等修饰器对 `duration` 的缩放是否影响设施 IO 的最终 Rate/s，取决于该设施端口的 `measure_mode`——而非作用于"所有东西"：

| `measure_mode` | 归化公式 | 受 duration 缩放影响？ | 物理直觉 |
|----------------|-----------|----------------------|----------|
| `per_cycle` | `amount / duration` | **是** | 配方原料/产物：配方跑得快，每秒吞吐自然高 |
| `rate_per_tick` | `amount × 20` | **否** | 持续效用（J/t）：消耗本质是每 Tick 计量 |
| `rate_per_sec` | `amount × 1` | **否** | 固定消耗（如冷却介质）：每秒固定消耗 |

这一规则由管线末尾的 `normalizeRate()` 函数统一执行，而非在每个修饰器中各自处理。

---

### 6.3 管线执行流程

#### 6.3.1 抽象流程

管线引擎在每次请求时按以下步骤执行：

| 步骤 | 操作 | 说明 |
|------|------|------|
| **Step 1** | 初始化 | 深拷贝原始配方数据，按 `is_utility` 标志隔离为四个独立数组，创建 `PipelineContext` |
| **Step 2** | 遍历修饰器 | 按 `active_modifiers` 数组顺序逐一调用 `evaluate(ctx, uiState)`，将返回的 `ModifierEffect` 立即施加到 `PipelineContext` 的对应字段 |
| **Step 3** | 归一化 | 对所有资源执行 `normalizeRate()`：根据各端口的 `measure_mode` 将 `amount` 转换为统一速率 Rate/s |
| **Step 4** | 结构化输出 | 产出 `ComputedNodePayload`，四维独立数组保持拆分 |

`evaluate()` 接收的是调用时刻已由前面所有修饰器修改过的 Context。当修饰器需要基于"当前状态"做决策时（如"并行后的能耗是多少 → 能否超频"），它读到的就是前面所有工序结算后的最新值。

---

#### 6.3.2 `measure_mode` 在归一化中的角色

Step 3 的 `normalizeRate()` 函数是管线中的核心防御逻辑：

- **`per_cycle`**：Rate/s = `amount / duration`。duration 缩短时 Rate/s 按公式放大。
- **`rate_per_tick`**：Rate/s = `amount × 20`。duration 的任何变化与它无关——J/t 本身就是速率量纲。升压只通过修饰器的定向 utility 倍率影响它。
- **`rate_per_sec`**：Rate/s = `amount`。既不受 duration 影响，也不受升压倍率影响。

---

### 6.4 修饰器接口与注册

每个修饰器实现 `IMachineModifier` 接口：

```typescript
interface IMachineModifier {
  id: string
  name: string
  compatible_archetypes?: string[]
  ui_schema?: ModifierUISchema[]          // UI 控件定义
  evaluate(
    inputs: Resource[],                   // 当前 PipelineContext 中的全部输入
    outputs: Resource[],                  // 当前全部输出
    durationSeconds: number,              // 当前 duration
    uiState: Record<string, unknown>      // 用户配置
  ): ModifierEffect
}
```

**接口不含执行顺序字段**。修饰器的执行顺序由 `active_modifiers` 数组的索引位置完全决定——数组前段先执行，后段后执行。UI 可通过拖拽重排数组顺序来改变执行链，无需修改任何修饰器代码。

新增修饰器只需实现此接口并注册到 `modifierRegistry`，无需修改管线核心逻辑。OmniFlow 的修饰器系统采用"引擎通用 + 模组可插拔"架构：

| 修饰器 ID | 类型 | 功能 |
|-----------|------|------|
| `base_chassis_efficiency` | 引擎内置（通用） | 机器底座效率系数——对 duration 和各 IO 数组施加线性乘数 |
| `chance_output` | 引擎内置（通用） | 概率副产物期望值缩放 |
| _（模组自定义）_ | 可插拔扩展 | 模组通过实现 `IMachineModifier` 注入特定逻辑 |

OmniFlow 核心发行版仅包含通用修饰器。游戏专属修饰器作为独立的扩展包存在，由模组配置文件或第三方扩展注册到 `modifierRegistry`。

---

### 6.5 示例推演

以下示例展示同一个五步修饰器链在实际配方数据上的具体推演。示例中的修饰器 ID 均为抽象占位符——不同游戏模组以各自的修饰器 ID 注册到 `modifierRegistry` 中。

---

#### 6.5.1 修饰器角色

以一个典型的五步链为例：

| 顺序 | 角色 | 功能 | 作用域 | 数学性质 |
|------|------|------|--------|----------|
| ① | 线性乘数（效率） | 产物 +25% / 时间 −50% | recipeOutputs 或 duration | 纯线性乘数 |
| ② | 线性乘数（底座系数） | 机器自带的效率系数 | 四数组 + duration | 纯线性乘数 |
| ③ | 并行处理器 | 按功率容量计算最大并行次数，等比放大 IO | 四数组全部（含 utility） | 整数离散 |
| ④ | 超频处理器 | 迭代判断功率阈值，逐级升压加速 + 限幅钳位 | duration + utility（定向） | 非线性/迭代 |
| ⑤ | 概率处理器 | 概率副产物的期望值折算 | recipeOutputs | 纯线性乘数 |

---

#### 6.5.2 并行与超频分离

并行和超频作为两个独立的修饰器顺序执行，`PipelineContext` 充当唯一的信息传递路径：

```
某机器的功率容量 512 J/t，基础配方耗能 24 J/t：

线性乘数 A 产出：utilityInputs[energy:utility_power].amount = 24
线性乘数 B 产出：utilityInputs[energy:utility_power].amount = 24（底座系数未影响该效用项）
    ↓
并行处理器：
  theoreticalParallel = floor(512 / 24) = 21
  · 四数组全部 × 21
  · utilityInputs[energy:utility_power].amount → 504  ← 写入 Context
    ↓
超频处理器：
  读取 utilityInputs[energy:utility_power].amount = 504
  while (504 × 4 ≤ 512)? → 否，停止迭代
  超频次数 = 0；结论：不超频（余量不足）
```

若将并行和超频合并为一个原子修饰器，它们共享的是**同一个基础值 24**而非 504——超频判断将完全错误。这正是将它们拆分为两个独立修饰器并将 `PipelineContext` 作为唯一状态通道的根本原因。

---

#### 6.5.3 完整数值推演

基础效用消耗 24 J/t，功率容量 512 J/t，配方耗时 10s：

| 步骤 | 操作 | 当前修饰器 | `utility[energy:utility_power].amount` | `dur` | `recipeIns[*]` |
|------|------|-----------|------------------------------|-------|----------------|
| 1 | 初始化 | — | 24 | 10.0 | 各 1.0 |
| 2a | 线性乘数 A：`recipeOutput × 1.25` | `mod_eff` | 24 | 10.0 | 各 1.0 |
| 2b | 线性乘数 B：`dur × 0.8`、`utility × 0.8` | `mod_base` | 19.2 | 8.0 | 各 1.0 |
| 2c | 并行：`floor(512/19.2)=26`，四数组 × 26 | `mod_par` | **499.2** | 8.0 | 各 26.0 |
| 2d | 超频：读取 499.2，`while(499.2×4≤512)→否` | `mod_oc` | 499.2 | 8.0 | 各 26.0 |
| 2e | 概率：期望值缩放 recipeOutputs | `mod_ch` | 499.2 | 8.0 | 各 26.0 |
| 3 | 归一化 | — | → **1248 J/s** | — | 3.25 /s |
| 4 | 结构化输出 | — | — | — | — |

补注：若基础效用消耗较小（如 4 J/t），并行 128 次后消耗为 512 J/t，超频处理器读到该值后会算出还能超频多次。

---

#### 6.5.4 顺序敏感性

即使两个修饰器在数学上"同类"，先后顺序也会产生截然不同的结果：

| 修饰器 | 行为 |
|--------|------|
| `conditional_boost` | 若当前 `durationSeconds > 5.0`，则 duration × 0.5 |
| `mod_overclock` | 迭代判断功率阈值，duration 连续 ÷ 4 直到触顶 |

**场景 A：`conditional_boost` 在前、`mod_overclock` 在后**

```
durationSeconds = 10.0
  → conditional_boost：10.0 > 5.0 → × 0.5 = 5.0
  → mod_overclock：读取 5.0，迭代超频……
```

**场景 B：`mod_overclock` 在前、`conditional_boost` 在后**

```
durationSeconds = 10.0
  → mod_overclock：超频迭代将 duration ÷ 4 = 2.5
  → conditional_boost：2.5 < 5.0 → 条件不触发，修饰器无效果
```

两种顺序得出完全不同的结果。用户通过 UI 自上而下排列修饰器，就是在精确决定这个行为。

## 7. 线性规划矩阵模型

本章是整个 OmniFlow 引擎的数学核心。前六章的所有架构设计——本体论分类、命名解析、四阶段生命周期、修饰器管线——最终都服务于一个目标：将玩家搭建的产线图精确编译为一个标准形式的线性规划问题。

---

### 7.1 化学计量矩阵定义

OmniFlow 采用经典的生产计划矩阵模型（Leontief Input-Output Model 的游戏变体）：

> **列 = 加工变量，行 = 物品 ID**
> **产出取正号（+），消耗取负号（−）**

记加工配方数量为 $R$，输入端数量为 $S$，输出端数量为 $T$，物品全集数量为 $M$。

**统一变量向量**：

$$
\mathbf{x} = \begin{bmatrix} x_0 & \dots & x_{R-1} & | & x_R & \dots & x_{R+S-1} & | & x_{R+S} & \dots & x_{R+S+T-1} \end{bmatrix}^\top
$$

其中：

| 变量段 | 物理意义 | 约束范围 |
|--------|----------|----------|
| $x_0 \dots x_{R-1}$ | 每个配方的机器台数（可小数，表示部分负载） | $[0, \text{upper}_i]$ |
| $x_R \dots x_{R+S-1}$ | 每个 Source 节点的实际吞吐速率 | $[0, \text{cap}_i]$ |
| $x_{R+S} \dots$ | 每个 Target 节点的实际消耗/产出速率 | 取决于模式 |

**化学计量矩阵** $\mathbf{A} \in \mathbb{R}^{M \times (R+S+T)}$：

- 对齐配方列：若配方 $j$ 产出物品 $i$（速率为 $v$），则 $\mathbf{A}_{i,j} = +v$；若配方 $j$ 消耗物品 $i$，则 $\mathbf{A}_{i,j} = -v$。
- 对齐 Source 列：$\mathbf{A}_{i, R+s} = +1.0$（Source $s$ 向系统注入物品 $i$）。
- 对齐 Target 列：$\mathbf{A}_{i, R+S+t} = -1.0$（Target $t$ 从系统取出物品 $i$）。

---

### 7.2 约束体系

#### 7.2.1 等式约束（Target 物品严格守恒）

对每一个有 Target 节点声明的物品 $i$，施加严格等式：

$$
\sum_{j=0}^{R+S+T-1} \mathbf{A}_{i,j} \cdot x_j = 0
$$

物理意义：该物品的 **净产量 + 净注入 − 净消耗 − 净流出 ≡ 0**，即恰好满足需求，无剩余无短缺。

#### 7.2.2 不等式约束（非 Target 物品允许溢出）

对于未被任何 Target 节点声明的物品 $i$，若存在正系数列（即至少有一个配方产出该物品），施加不等式：

$$
\sum_{j=0}^{R+S+T-1} \mathbf{A}_{i,j} \cdot x_j \geq 0
$$

物理意义：副产物可以溢出（无需求时不强制平衡），但不能出现净赤字。若某物品在所有列中均为零或全负（纯消耗且无 Source），则跳过约束——视为隐式无限供给。

---

### 7.3 目标函数

OmniFlow 默认最小化总机器负载，并在不同 Target 模式下差异化目标：

| Target 模式 | 目标系数 $c_i$ | 含义 |
|-------------|---------------|------|
| `demand`（默认） | $c_i = 0$（对 Target 变量） | 精准满足需求，不额外优化 |
| `maximize` | $c_i = -10000$（对 Target 变量） | 强最大化产出 |
| `overflow` | $c_i = 0$（对 Target 变量） | 消纳模式：纯质量平衡驱动，不施加任何增减倾向 |
| 配方变量（`auto` 模式） | $c_i = 1$ | 最小化机器配置总量 |

> **为什么 overflow 的成本是零而不是正数或负数？** 消纳模式的本意是"来多少接多少，不做取舍"。若设为正值（如 $0.001$），求解器会被激励去**减少**该 Target 的吸收量——这在多配方可选时会扭曲配方选择，使其回避产出该副产物的路径。若设为负值（如 $-0.001$），求解器会**主动多产**来投喂 overflow——这不再是消纳，而是变相的无上限需求。零成本保留最纯正的语义：变量值完全由物料平衡方程决定，求解器对此既不鼓励也不惩罚。

最终标准形式：

$$
\begin{aligned}
\min \quad & \mathbf{c}^\top \mathbf{x} \\
\text{s.t.} \quad & \mathbf{A}_{\text{ub}} \mathbf{x} \leq \mathbf{b}_{\text{ub}} \\
& \mathbf{A}_{\text{eq}} \mathbf{x} = \mathbf{b}_{\text{eq}} \\
& \mathbf{0} \leq \mathbf{x} \leq \mathbf{u}
\end{aligned}
$$

---

### 7.4 变量边界（Bounds）与模式语义

| 变量类型 | 模式 | 下界 | 上界 |
|----------|------|------|------|
| Recipe | `auto` | 0 | $+\infty$（自由缩放） |
| Recipe | `limit` | 0 | `manual_machines`（手动指定上限） |
| Source | `infinite` | 0 | $+\infty$（无限矿/无限水） |
| Source | `limit` | 0 | `amount`（有限供给） |
| Target | `demand` | `amount` | $+\infty$（至少满足需求，可超产） |
| Target | `maximize` | 0 | $+\infty$（无上限最大化） |
| Target | `overflow` | 0 | $+\infty$（消纳溢出） |

---

### 7.5 求解与结果回代

使用 `scipy.optimize.linprog`（highs 方法）求解。求解完成后执行全量矩阵回代：

$$
\mathbf{r}_{\text{net}} = \mathbf{A}_{\text{full}} \cdot \mathbf{x}^*
$$

其中 $\mathbf{A}_{\text{full}} \in \mathbb{R}^{M \times (R+S+T)}$ 为完整化学计量矩阵。回代结果 $\mathbf{r}_{\text{net}}$ 按正/负拆分：

- $\mathbf{r}_{\text{net}}[i] > 0$ → 系统净产出，入 `system_outputs`
- $\mathbf{r}_{\text{net}}[i] < 0$ → 系统净消耗，取绝对值入 `system_inputs`

配方变量结果按 $\texttt{Math.ceil}(x_i - \varepsilon)$ 向上取整为整数机器数，同时计算利用率 `utilization = exact / actual`。

特殊状态处理：

| 求解状态 | 含义 | 前端反馈 |
|----------|------|----------|
| `success` | 找到最优解 | 展示完整结果 |
| `infeasible` | 约束冲突，无可行解 | 提示检查供需是否矛盾 |
| `unbounded` | 存在最大化 Target 但缺乏物理瓶颈 | 提示为上游机器或 Source 设定产能上限 |

---

### 7.6 CapEx 与 OpEx 的数学边界

矩阵模型自然揭示了 CapEx 与 OpEx 的分离逻辑：

| 概念 | 内容 | 数学处理 |
|------|------|----------|
| **OpEx（运营成本）** | 每秒消耗的物质与能量 | 进入稳态矩阵，作为变量系数或约束参与 LP 求解 |
| **CapEx（建厂成本）** | 机器造价、`consumable: false` 的物品 | 不进矩阵。前端编译时剔除，汇总为一次性物料清单（BOM） |

`consumable: false` 的资源（如编程电路板、模具）在修饰器管线的最终归一化步骤中被明确处理——`normalizeRate` 函数检测到此标记后直接返回 0，确保它们在 `flattenForBackend` 时被过滤，不进入矩阵。

---

### 7.7 可扩展性：维度诅咒与分块求解

以上模型将所有配方、Source、Target 拍平进一个大矩阵进行全局求解，在数学上保证全局最优，但面临规模上限。

---

#### 7.7.1 当前性能边界

`scipy.optimize.linprog`（highs 方法）采用修正单纯形法，在稀疏约束矩阵上具有准线性时间的实践经验：

| 规模 | 变量数 | 约束行数 | 典型耗时 | 对应场景 |
|------|--------|----------|----------|----------|
| 小型 | < 200 | < 500 | < 10 ms | 单产线、格雷科技多方块规划 |
| 中型 | 200–800 | 500–2000 | 10–50 ms | 多产线耦合、中等工厂 |
| 大型 | 800–3000 | 2000–8000 | 50–200 ms | 《异星工厂》千瓶/分钟级 |

对于绝大多数硬核模组玩家的实际产线规模（通常 50–200 个配方节点），当前拍平求解完全在可接受范围内。挑战出现在用户将多个子工厂完整建模在同一张画布上，或批量仿真大型整合包时。

---

#### 7.7.2 为什么并非每一个玩家都在"维度诅咒"区间

OmniFlow 避免了几个关键的规模膨胀因素：

**① 物品 ID 的行维度由 Net 隔离控制，而非配方数放大。** 第 8.1 节的连通分量检测确保同一 Net 内的所有端口共享一个唯一的矩阵行。如果没有 Net 隔离，$R$ 个配方各有 $k$ 个端口会生成 $O(R \cdot k)$ 行；有 Net 隔离后，行数等于连通分量数 + 全局总线数，通常比配方数还小。

**② Source/Target 列为 $\mathcal{O}(S+T)$ 而非 $\mathcal{O}(R \cdot k)$。** 每个 Source 和 Target 各占一列，不随物品种类膨胀。变量总数 $R+S+T$ 通常远小于用户直观感受的"端口总数"。

**③ `consumable: false` 在编译前剔除。** 减少了矩阵中"零值列"和"非零但无关的行"，降低了稀疏矩阵的填充度。

综合来看，一个 200 配方的画布的矩阵规模约为 $300~600 \times 300~600$，仍在可接受范围内。

---

#### 7.7.3 未来扩展路径：分层分区求解（Hierarchical Decomposition）

当规模确实超出单次 LP 的实用上限时，可在拓扑编译阶段引入层次化分解。这一策略本质上是利用第 8 章已构建的 Net 拓扑，将全局问题降维为一系列子问题：

**第一步：强连通分量（SCC）分区。**

利用 Tarjan 算法或 Kosaraju 算法扫描 Net 连通图，将产线拆分为一组拓扑有序的强连通分量。每个 SCC 内部是物料循环耦合最紧密的区域；SCC 之间只有单向物料流动。

**第二步：按拓扑序级联求解。**

从最高 SCC（无上游依赖的子图）开始，对每个分量进行独立的局部 LP 求解。输出结果（净产出速率）作为下游 SCC 的边界条件，沿拓扑序逐级传递。

**第三步：全局一致性校验（可选）。**

所有 SCC 求解完成后，回代全局矩阵验证是否满足跨分区约束。若出现不一致，标记为"需要全矩阵求解"并回退至单次 LP。

**分层求解的优点**：

- 每个子矩阵规模可控，求解时间接近 $\mathcal{O}$(每个 SCC 大小之和) 而非 $\mathcal{O}$(全图大小)
- SCC 内部的循环和副产物溢出仍由 LP 精确求解，数学最优性的损失仅发生在 SCC 边界——边界条件取上游 SCC 的真实产出，不做过度近似
- 拓扑排序确保求解顺序与物理物料流一致，符合玩家"先上游后下游"的自然思维模型

**分层求解的代价**：

- 仅在 SCC 边界截断处可能产生微小次优——如果上游 SCC 在某种全局配置下可以调整自己的产出以更匹配下游需求，这种协同优化会被边界隔离所屏蔽
- 工程复杂度显著增加，需要维护 SCC 拓扑图和跨分区的状态传递

对 OmniFlow 当前阶段而言，分层求解作为**架构预留扩展点**存在：前端拓扑编译（第 8 章）已产出 Net 连通图，此图可直接作为 SCC 分区的输入，无需重新构建整套数据结构。

## 8. 拓扑网络 → 矩阵的编译规则

第 7 章定义了矩阵的数学形式，本章解决其构造前提：**React Flow 画布上的节点与边，如何映射为矩阵中的变量 ID 与约束关系。**

---

### 8.1 连通分量与 Net 隔离

OmniFlow 借鉴 EDA（电子设计自动化）中的"网表（Netlist）"概念：每一组通过物理连线连接在一起的端口共享一个全局唯一的 Net ID。这防止了后端矩阵求解器将不同连通子图中恰好共享同一物品 ID 的资源错误地合并。

**核心算法**：基于边（Edge）的并查集（Union-Find）连通分量检测。

```
对于每条物理连线 (sourceHandle → targetHandle):
  将 source-port-key 与 target-port-key 联合 (Union)

遍历所有节点的所有端口:
  若端口在连线中出现 → 分配 Net_<资源ID>_<短哈希>
  若端口标记为 global 路由 → 分配 Global_<资源ID>  （注意：是完整的物质标识符如 "energy:mod_power"，而非抽象量纲 "energy"）
  若端口无任何连线 → 分配 Void_<节点ID>_<资源ID>
```

三种 Net 类型的区别：

| Net 类型         | 命名格式                 | 含义            | 矩阵行为                                                                                                                |
|----------------|----------------------|---------------|---------------------------------------------------------------------------------------------------------------------|
| **Wired Net**  | `Net_<id>_<hash>`    | 一组通过物理连线互联的端口 | 所有同 Net 的端口视为共享同一物流通道                                                                                               |
| **Global Bus** | `Global_<id>`        | 全局隐式共享网络      | 同一 **物质 ID** 的所有 global 端口自动聚合为该物质的全局虚拟源/汇。不同的物质各自拥有独立的全局总线——`Global_energy:power_a` 与 `Global_energy:power_b` 互不干扰 |
| **Void**       | `Void_<nodeId>_<id>` | 孤立端口          | 视为对空排放（后端忽略）                                                                                                        |

---

### 8.2 路由模式与全局管网

OmniFlow 支持两种路由范式，从拓扑编译角度简化了画布复杂度：

| 路由模式     | 语义              | 编译处理                                                                                                                                                                     |
|----------|-----------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `wired`  | 必须建立物理拓扑连线      | 通过并查集检测连通分量，分配 Net 标识                                                                                                                                                    |
| `global` | 全局隐式共享网络（如电力总线） | 同一 **物质 ID** 的 global 端口自动聚合并入 Global 虚拟源/汇。不同物质各自独立：`energy:power_a` 和 `energy:power_b` 虽同属 `energy` 量纲，但进入 `Global_energy:power_a` 与 `Global_energy:power_b` 两条互不干扰的总线 |

**全局管网的自动化处理**：当系统检测到某个物质 ID 的端口标记为 `global` 路由时，前端无需手动创建该物质的输入节点。计算引擎自动为该**具体物质**（如 `energy:power_a`，而非抽象量纲 `energy`）生成虚拟 Source 和虚拟 Target，在后端矩阵中表现为该物质独立总线的供需平衡约束。不同物质 ID 的 global 端口各自拥有独立总线，在矩阵中互不耦合。

---

### 8.3 Source / Target 的约束注入

Source 节点和 Target 节点在编译后以独立列的形式注入矩阵变量向量：

**Source 节点**：
- 在化学计量矩阵中占一列，列系数为 $+1.0$（向系统注入物品）
- 上界由模式决定：`infinite` → 无上限，`limit` → `amount`
- 求解后取整，负值钳位为 0

**Target 节点**：
- 在化学计量矩阵中占一列，列系数为 $-1.0$（从系统取出物品）
- 若模式为 `demand`，下界设置为 `amount`（硬性需求约束）
- 该 Target 涉及的物品 ID 被归入 `target_items` 集合，触发等式约束

---

### 8.4 循环 / 回收网络

OmniFlow 的矩阵模型天然兼容循环回收网络。当一个配方的产出被连接到另一个配方的输入时，拓扑编译器通过 Net 名称将两者关联。在矩阵中，同一 Net 的端口共享同一物品 ID，线性规划引擎在求解时自动平衡该物品的产耗。

**循环的数学本质**：不在矩阵中引入新变量，而是通过等式约束 $\mathbf{A}_i \mathbf{x} = 0$ 自然形成环状平衡——产出项与消耗项互相制约，求解器在全局最优解中自动确定循环的稳态流量。

---

### 8.5 编译规则附录：概念到矩阵的翻译

前七章从概念层和数学层定义了系统的运行方式，本节补全从"概念"到"具体矩阵操作"的翻译步骤，覆盖状态约束消解、并行数预计算、IO 列表动态变化和 LP 模型假设边界。这些规则将白皮书各章串联为一条完整的编译路径。

---

#### 8.5.1 状态/阈值型约束的消解

第 2.2.3 节将状态/阈值型资源定义为"稳态物质通量恒为零"。在当前纯 LP 实现中，这些约束不进入矩阵，通过以下三种方式在前端消解：

| 消解方式 | 判定条件 | 编译行为 | 示例 |
|----------|----------|----------|------|
| **资格鉴定** | 约束是二进制准入条件（满足/不满足），无数量维度 | 前端检查用户配置 → 未满足则节点灰显、配方从编译中排除 | "必须处于末地维度"：用户未勾选时该配方节点不参与求解 |
| **乘数转化** | 约束有数量效应（如"温度愈高效率愈高"），可表达为连续函数 | 前端将其折叠为一个 `statMultiplier` 修饰器，排在修饰器列表的前段，温度值本身不进矩阵 | "温度 > 1000K 时效率 +20%"：编译为 `stat.duration = 0.833` |
| **限幅钳位** | 约束对某个修饰器施加硬上界 | 前端在该修饰器的迭代逻辑中作为 `break` 条件 | "超频最多 2 级"：超频修饰器的 `while` 循环以 `ocCount < 2` 为附加终止条件 |

关键声明：

> **当前版本所有状态/阈值型约束均在前端编译阶段消解，后端矩阵为纯连续 LP。** 未来若引入"求解器在多个离散选项中自主选择"（如自动选择能源仓等级），则需升级为 MILP。

---

#### 8.5.2 并行数的预计算性质

第 6 章的并行修饰器产生一个并行乘数，管线将其应用到四数组的所有 `amount` 上。编译顺序如下：

```
用户在画布上配置"功率容量"（如 256 J/t，2 通道）
                              ↓
          拓扑编译阶段：并行数 = floor(功率总容量 / 单配方基础消耗)
          （基础消耗取自修饰器列表中位于"并行"前方的修饰器产出的 PipelineContext）
                              ↓
          管线按修饰器顺序执行到并行处理器：将并行数作为固定乘数应用到 IO
                              ↓
          拍平后送入矩阵：配方列系数已是"并行 × 基础速率"的最终值
```

关键声明：

> **并行数是拓扑编译阶段根据用户手动配置的"功率容量"预先锁定的常数，不是后端求解器的决策变量。** 后端矩阵中每个配方只有一个变量 $x_j$（机器台数），而非"并行数 × 机器台数"的两个独立变量。求解器决定的是"在这个功率配置下，开几台这样的机器"。

**为什么不是循环依赖**：并行数依赖的"总功率"来自用户的配置（如 `power_config: { wattage: 256, channels: 2 }`），而非全局管网的求解结果。全局管网在矩阵求解后才得出"系统总能量是否足够"——这是瓶颈报告，不是并行数的输入。顺序上是：用户配置功率容量 → 编译确定并行数 → 矩阵求解 → 报告能量是否够用。

---

#### 8.5.3 超频引发的 IO 列表变化——修饰器自有能力

第 6 章的超频修饰器通过缩放 `duration` 和 `utility` 产生加速效应。在绝大多数情况下，这是**纯量变**——所有 IO 速率等比例变化，配方列的内部比例不变。但某些模组的配方在特定加速档位下可能发生 IO 列表的增减：新增一种副产物，或移除一个输入项。

这**不是**拓扑编译层的职责——它是修饰器 `evaluate()` 的自有能力。`evaluate()` 接收 `PipelineContext` 中的可变数组（`inputs[]`、`outputs[]`），修饰器可以直接原地增删条目：

```
modifier.evaluate(inputs, outputs, durationSeconds, uiState):
  // 1. 根据 uiState.tier 和当前 durationSeconds 做超频迭代
  // 2. 根据超频档位决定是否增删 IO：
  if (tier >= 2) {
    outputs.push({ id: "item:D", amount: 10, ... })  // 新副产物
  }
  if (tier >= 3) {
    inputs = inputs.filter(r => r.id !== "item:catalyst")  // 移除催化剂需求
  }
  return { durationMultiplier, utilityMultipliers, ... }
```

管线将这些修改后的数组直接归一化并送入矩阵。一个配方节点始终只产生**一个矩阵列**——列的内容（哪些物品、多少系数）完全由修饰器链在运行时动态决定，不需要引擎做"编译时配方列分支"。

> **设计原则**：IO 列表的增删是修饰器的域内逻辑，不是引擎的功能。引擎只负责按序执行修饰器并对最终产出的四数组做归一化与拍平。

---

#### 8.5.4 LP 模型的工程假设边界

矩阵模型（第 7 章）基于以下假设，超出边界的问题需在前端预处理或作为未来扩展：

| 假设 | 声明 | 边界外的处理 |
|------|------|-------------|
| **稳态** | 所有变量独立于时间，不模拟启动/停机瞬态 | 带启动条件的循环由前端注入最小机器数下界（`bounds[i] = (1, ∞)`）或等效 CapEx 约束 |
| **无缓存上限** | 物品可无限囤积于隐式缓冲区 | 若某物品的缓存有上限，需由前端在拓扑编译时注入额外的"溢出消纳 Target"或产能上限 |
| **列系数固定** | 一个配方列对每个物品的净速率在求解期内为常数 | 若 IO 列表在修饰器链中发生增减，修饰器在 `evaluate()` 中原地完成修改（见 8.5.3），管线归一化后的列系数即为最终值 |
| **线性独立** | 配方列之间无乘积交叉项（如"配方 A 的产出受配方 B 的机器数影响"） | 当前所有修饰器效果在管线阶段已结算为固定系数，不会产生列间耦合。若未来引入"邻接加成"类机制，需在编译前结算为等效系数 |
| **无最小启动量** | 机器数可为任意非负实数（求解后取整），不要求整数 | 热循环等场景若需"机器数 ≥ 1 才能维持温度"，需由前端在变量边界中注入最小下界 |

**循环网络的特别说明**：第 8.4 节描述的循环在稳态假设下自然可解。但若循环涉及热依赖（产出热量 → 同一机器消耗热量 → 没有热量机器不启动 → 不启动就没有热量），LP 的平凡解 $x=0$（不建任何机器）在数学上合法但在物理上无意义。此类循环需由前端注入 $x \geq 1$ 的最小机器数边界，或将其作为"冷启动成本"（CapEx）单独报告。

## 9. 节点图编辑器

### 9.1 React Flow 画布与节点类型

OmniFlow 的前端基于 React Flow 构建可视化节点图编辑器。画布支持三种节点类型：

| 节点类型 | 标识 | 功能 |
|----------|------|------|
| **SourceNode** | 绿色输入源 | 定义系统的外生输入（无限矿、有限供给） |
| **RecipeNode** | 蓝色加工节点 | 定义物质转换配方（输入 → 机器 → 输出） |
| **TargetNode** | 橙色目标节点 | 定义系统的最终需求（指定产出物品与速率） |

节点通过边（Edge）连接，每条边的 `sourceHandle` 和 `targetHandle` 携带流转物品的 ID，构成拓扑编译的输入数据。

**状态管理**：画布状态完全由 React Flow 的 `useNodesState` / `useEdgesState` 接管，结合 Zustand 实现资源注册表的细粒度订阅——组件仅在所引用的资源类别变化时重渲染，确保拖拽操作的流畅性。

---

### 9.2 基建区与加工区的 UI 语义保持

Recipe 节点在编辑面板中呈现两个语义分明的区域，直接映射白皮书第 2.3 节的基建/加工划分：

| UI 区域 | 数据来源 | 编辑权限 |
|---------|----------|----------|
| **上半部：加工区（Recipe IO）** | 配方定义 | 用户可编辑（配比、概率、催化剂标记） |
| **下半部：基建区（Utility IO）** | 底盘原型（Archetype） | 根据 Archetype 的 `amount_mutable` 属性决定是否可编辑 |

`consumable: false` 的资源在加工区中以灰色 $0\text{/s}$ 显示并附带非消耗标记，在基建区中根据路由模式（`global` / `wired`）隐式连线或显式展示。

---

### 9.3 SystemHUD 与全局管网可视化

SystemHUD（系统状态抬头显示器）是连接矩阵求解结果与用户感知的桥梁。它遍历求解返回的 `system_inputs` 和 `system_outputs`，按量纲聚合显示整个产线的全局物流摘要：

- 按量纲（item / fluid / energy）分组展示系统级净输入/净输出
- 借助 `dimension:asset` 字典解析每条物流的单位与颜色
- 高亮瓶颈资源——净消耗速率接近系统总供给上限的物品
- 展示全局电力总消耗与总供给的差值

## 10. 扩展机制

### 10.1 模组插件架构

OmniFlow 的核心引擎不包含任何硬编码的游戏逻辑，所有模组特定行为通过三个可插拔的扩展点注入：

| 扩展点 | 机制 | 示例 |
|--------|------|------|
| **资源注册表** | 在 `ResourceRegistry` 中声明模组特定资产的单位覆盖与量纲归属 | `mod_power` → `unit: EU` |
| **机器底盘原型（Archetype）** | 定义模组特定机器的固定设施（`fixed_utilities`）、默认修饰器 | 某模组电力机器：`fixed_utilities: { energy:mod_power }` |
| **修饰器（Modifier）** | 实现 `IMachineModifier` 接口，注入模组特定的物理仿真逻辑 | 某模组并行处理器：功率容量 → 计算最大并行次数 → 四数组等比放大 |

新增模组支持只需配置这三个扩展点，核心管线、矩阵求解器无需任何代码改动。

---

### 10.2 多语言本地化（i18n）

OmniFlow 的本地化设计遵循三级级联架构（与资源解析同构）：

| 级别 | 内容 | 优先级 |
|------|------|--------|
| **Tier 1：资源显式翻译** | 特定资产 ID 的专门译名（如 `mod_power` → "模组能量"） | 最高 |
| **Tier 2：量纲默认翻译** | 量纲级别的通用显示名（如 `energy` → "能量"） | 中 |
| **Tier 3：原 ID 回退** | 未翻译时直接显示 ID 原文 | 最低 |

这种设计确保了即使新增未知模组资源，UI 也始终能够显示有意义的信息。

---

### 10.3 CapEx 物料清单（BOM）

OmniFlow 将 `consumable: false` 的资源（编程电路板、模具、透镜等）排除在稳态矩阵之外，但提供专门的 CapEx 物料清单面板，将以下项汇总为一次性建厂清单：

- 所有配方节点的 `consumable: false` 物品（每种仅计 1 次）
- 所有 Source 节点的机器造价（若已录入）
- 所有 Recipe 节点的机器造价（若已录入）

CapEx BOM 独立于 OpEx 运营矩阵，玩家可导出为物料清单，实现"建厂"与"运营"的彻底分离。

## 附录 A. API 契约

### A.1 请求格式

`POST /api/calculate`

```jsonc
{
  "nodes": [
    {
      "id": "node-1",                    // 节点唯一标识
      "type": "recipeNode",              // "recipeNode" | "sourceNode" | "targetNode"
      "data": {
        // ── RecipeNode 特有 ──
        "recipe_id": "mod:my_recipe",
        "machine_name": "示例机器",
        "system": "my_game",
        "duration_ticks": 20.0,          // 归一化后固定为 20 (rate/s)
        "inputs": {                       // Dict[category:id, rate/s]
          "item:raw_material": 1.0
        },
        "outputs": {
          "item:product": 0.8
        },
        "mode": "auto",                  // "auto" | "limit"
        "manual_machines": null,         // mode=limit 时的机器数上限

        // ── metadata (模组特定——键值对由模组的修饰器定义和消费) ──
        "metadata": {
          "energy_per_tick": 120,
          "tier": "medium",
          "can_boost": true
        }
      }
    },
    {
      "id": "src-1",
      "type": "sourceNode",
      "data": {
        "id": "item:raw_material",
        "amount": 10.0,                  // 最大供应速率
        "mode": "infinite"               // "infinite" | "limit"
      }
    },
    {
      "id": "tgt-1",
      "type": "targetNode",
      "data": {
        "id": "item:product",
        "amount": 2.0,                   // 目标需求速率
        "mode": "demand"                 // "demand" | "maximize" | "overflow"
      }
    }
  ],
  "edges": [
    {
      "source": "src-1",
      "target": "node-1",
      "sourceHandle": "item:raw_material", // 流转物品 ID
      "targetHandle": "item:raw_material"
    }
  ]
}
```

### A.2 响应格式

```jsonc
{
  "status": "success",                   // "success" | "infeasible" | "unbounded"
  "node_results": {
    "mod:my_recipe": {
      "machines_exact": 2.5,             // 精确机器数（允许小数）
      "machines_actual": 3,              // 向上取整后的整数机器数
      "utilization": 0.833               // 利用率 = exact / actual
    },
    "src-1": {
      "actual_amount": 5.0               // Source 实际吞吐量
    },
    "tgt-1": {
      "actual_amount": 2.0               // Target 实际满足量
    }
  },
  "system_inputs": {                      // 全系统净消耗
    "item:raw_material": 5.0,
    "energy:example_power": 360.0
  },
  "system_outputs": {                     // 全系统净产出（不含 Target 已消耗的）
    "item:byproduct": 0.5
  }
}
```

### A.3 节点模式速查

| 节点类型 | 模式 | 含义 |
|----------|------|------|
| Source | `infinite` | 无限供给，变量上界 = +∞ |
| Source | `limit` | 有限供给，变量上界 = amount |
| Recipe | `auto` | 自动缩放机器数，变量无上界 |
| Recipe | `limit` | 手动指定机器数上限 `manual_machines` |
| Target | `demand` | 精准满足需求，变量下界 = amount |
| Target | `maximize` | 强最大化产出，目标系数 = −10000 |
| Target | `overflow` | 溢出消纳，目标系数 = 0（纯质量平衡驱动） |

## 附录 B. 术语表

| 术语 | 英文 | 定义 |
|------|------|------|
| **量纲** | Dimension | 决定物质数学本质的物理类别（item / fluid / energy / stress / heat） |
| **单位** | Unit | 量纲在具体模组语境下的显示形式（EU / RF / mB / 个） |
| **底盘原型** | Archetype | 定义机器固定设施（`fixed_utilities`）和默认修饰器的模板 |
| **基建插槽** | Infrastructure Port | 维持机器运转所需的资源接口（冷却水、电力） |
| **加工插槽** | Payload Port | 执行物质转换所需的资源接口（配方原料、产出） |
| **修饰器** | Modifier | 对配方状态进行物理仿真的黑盒处理器 |
| **顺序管线** | Sequential Pipeline | 修饰器按 `active_modifiers` 数组的索引顺序（即 UI 列表自上而下的顺序）逐一执行，前一修饰器的 `PipelineContext` 修改直接传递给后一修饰器 |
| **拓扑编译** | Topological Compilation | 将 React Flow 节点图通过并查集转换为 Net 命名的过程 |
| **Net** | Net | EDA 概念——一组物理连通的端口共享的唯一网络标识 |
| **全局管网** | Global Bus | 同一 **物质 ID**（如 `energy:mod_power`）的 `routing_mode: global` 端口自动聚合为该物质的独立共享网络。不同物质各自拥有独立总线 |
| **化学计量矩阵** | Stoichiometric Matrix | 列=配方、行=物品、产出正、消耗负的 LP 系数矩阵 |
| **线性规划** | Linear Programming (LP) | 在约束条件下求目标函数极值的运筹学方法 |
| **CapEx** | Capital Expenditure | 建厂成本——一次性投入（机器造价、模具） |
| **OpEx** | Operational Expenditure | 运营成本——稳态消耗速率，进入矩阵求解 |
| **Rate/s** | Rate per Second | OmniFlow 的统一归一化单位——每秒净速率 |
| **SystemHUD** | System Heads-Up Display | 展示全局物流摘要与瓶颈分析的 UI 面板 |
| **BOM** | Bill of Materials | 物料清单——CapEx 的一次性投入清单 |
