# OmniFlow 技术设计文档

***

## 1. 设计目标与范围

### 1.1 系统界定

OmniFlow 是一个可视化产线矩阵求解器。前端基于 React Flow 构建节点图编辑器，后端以 FastAPI 承载 SciPy 线性规划（Linear Programming，LP）求解。系统将用户搭建的产线图编译为标准形式 LP 问题并求解，返回全局最优的机器台数与物流速率配置。

### 1.2 涵盖内容

- 资源分类体系：物理性质维度 + 绑定上下文维度
- 标识符格式、类别注册表与解析回退链
- 资源生命周期：定义层 → 管线层 → 视图层 → 传输层的四阶段不可逆流转
- 修饰器管线：顺序执行接口、归一化规则
- 拓扑编译：连通分量检测、Net 隔离、路由模式
- LP 矩阵模型：化学计量矩阵、约束体系、目标函数、求解与回代
- 前端节点图编辑器的节点类型与 UI 数据映射
- 扩展机制：模组插件架构、i18n 级联、CapEx 物料清单
- API 契约与术语表

### 1.3 未涵盖内容

- 具体游戏的配方数据、模组资产定义
- 部署基础设施、CI/CD 配置
- 用户操作手册或教程

## 2. 关键决策与权衡

### 2.1 技术选型

| 决策点 | 选型 | 理由 |
|---|---|---|
| 前端画布 | React Flow | 节点图编辑范式成熟，内置拖拽、连线、缩放；Zustand 做资源注册表细粒度订阅，避免全局重渲染 |
| 后端求解器 | SciPy `linprog`（highs 方法） | 修正单纯形法在稀疏矩阵上准线性时间；Python 生态与 FastAPI 集成成本低 |
| 前后端通信 | FastAPI + REST（单端点 `POST /api/calculate`） | 前端完成全部业务逻辑（归一化、修饰器管线、拓扑编译），后端仅接收标准形式 LP 并求解 |
| 修饰器架构 | 顺序管线（Sequential Pipeline） | 修饰器之间存在状态依赖（如并行数影响超频判断），声明式/并行执行无法保证确定性 |
| 求解模型 | 纯连续 LP | 覆盖现阶段所有需求；MILP 路径作为架构预留，当前所有离散约束（状态/阈值型）在前端编译阶段消解 |

### 2.2 未选择方案

| 方案 | 不选理由 |
|---|---|
| 自定义单纯形求解器 | 开发与验证成本远高于复用 SciPy；HiGHS 求解器在工业界验证充分 |
| OR-Tools | 功能过剩（整数规划、约束规划），引入 C++ 扩展增加部署复杂度；当前纯 LP 场景 SciPy 足够 |
| 修饰器声明式配置（标签叠加） | 并行与超频存在顺序依赖（见 5.2 节），标签式无法建模"前一工序的结果作为后一工序的输入" |
| 全矩阵一次性求解（无 Net 隔离） | 不同连通子图的同名物品会被错误合并，导致不可行解 |

### 2.3 性能边界

| 规模 | 变量数 | 约束行数 | 典型耗时 | 对应场景 |
|---|---|---|---|---|
| 小型 | < 200 | < 500 | < 10 ms | 单产线、格雷科技多方块规划 |
| 中型 | 200–800 | 500–2000 | 10–50 ms | 多产线耦合、中等工厂 |
| 大型 | 800–3000 | 2000–8000 | 50–200 ms | 异星工厂千瓶/分钟级 |

对于实际产线规模（通常 50–200 个配方节点），单次求解耗时在可接受范围内。规模膨胀因素由以下机制控制：

1. 物品 ID 的行维度由 Net 隔离控制，而非配方数放大。同一 Net 内所有端口共享一个矩阵行。
2. Source/Target/Spill 列为 O(S+T+K)，非 O(R·k)。
3. 消耗几率为 0 的资源在编译前剔除。

### 2.4 架构预留：分层分区求解

当规模超出单次 LP 实用上限时，拓扑编译产出的 Net 连通图可直接作为强连通分量（SCC）分区的输入。求解流程为：

1. Tarjan 算法扫描 Net 连通图，拆分为拓扑有序的 SCC。
2. 从无上游依赖的最高 SCC 开始，逐级局部 LP 求解，将净产出速率传递至下游 SCC 边界。
3. 可选全局一致性校验，不一致时回退单次全矩阵求解。

代价：SCC 边界截断处可产生微小次优；工程复杂度增加。当前阶段不实现，作为架构预留扩展点。

## 3. 总体架构

### 3.1 三层架构

系统分为三个单向依赖层，无循环引用：

| 层级 | 职责 | 输入 | 输出 |
|---|---|---|---|
| 字典层（Global Registry） | 描述实体元数据（单位、颜色、类别） | 无依赖 | 纯实体定义 |
| 节点层（Node Definition） | 将实体接入具体语境（基建插槽 / 加工插槽） | 字典引用 + 底盘原型 + 配方 | 语境化资源列表 |
| 引擎层（Solver） | 接收归一化向量，求解全局最优 | 拍平后的 `Dict[id, rate]` | 每节点机器数 & 实际吞吐量 |

## 4. 资源分类体系

### 4.1 物理与数学性质维度（Nature Dimension）

所有资源按数学形态归入三类，不关心使用语境：

#### 4.1.1 累积量 / 流量型（Volumetric / Consumable）

- 离散数量计量（pcs、L），消耗即减少，可囤积于容器。
- 稳态通量定义为 Rate = Amount / Duration。
- 作为物料平衡方程的输入输出项，化学计量矩阵系数的直接来源。
- 典型实例：铁矿石、水、原油、维护备件。

#### 4.1.2 连续率 / 驱动型（Continuous Rate / Driving Force）

- 连续能量流形式存在（J/t、N·m），不可囤积，断开则关联机器停机。
- 表征本身即为速率量纲，无需额外转换。
- 作为 LP 约束边界：总消耗 ≤ 总供给，总产出 ≥ 总需求。
- 典型实例：电力（EU/t）、机械应力（SU）、热功率（HU/t）。

#### 4.1.3 状态 / 阈值型（State / Threshold）

- 环境门槛或启动判据，不消耗、不产出、不流转。
- 稳态物质通量 ≡ 0。
- 在前端编译阶段消解，不进入后端 LP 矩阵。消解规则：
  - **资格鉴定**：二进制准入条件（满足/不满足），未满足时配方节点从编译中排除。
  - **乘数转化**：可表达为连续函数的数量效应，折叠为 `statMultiplier` 修饰器。
  - **限幅钳位**：作为修饰器迭代逻辑中的 `break` 条件。
- 当前版本为纯连续 LP。未来若引入求解器自主离散选择（如能源仓等级），需升级为混合整数线性规划（MILP）。
- 典型实例：机器温度 > 1000K、必须处于"末地"维度、无尘室等级 ≥ 3。

### 4.2 绑定上下文维度（Context Dimension）

资源本身无"底盘/配方"之分，节点插槽（Port）赋予身份。

#### 4.2.1 基建插槽（Infrastructure Port / Chassis Bound）

- 维持机器运转，与配方选择无关。
- 数据来源：机器底盘原型（Archetype）的 `fixed_utilities` 声明。
- 并行执行多份配方时，基建消耗等比例放大。

#### 4.2.2 加工插槽（Payload Port / Recipe Bound）

- 实现物质转换，数据来源为配方声明。
- 配方更换时插槽内容随之更换。

两个插槽可同时引用字典中同一 `water` 条目，各自声明独立数量和速率。

### 4.3 催化剂与工具

催化剂/工具是介于累积量与阈值型之间的特殊形态。处理方式：在配方输入定义中声明消耗几率（0 到 1 之间的数值），表示每次加工期望消耗此物品的比例。

- 消耗几率 = 1：同普通原料，每次全额消耗。
- 消耗几率 ∈ (0, 1)：每次以此比例消耗。例如锤子总耐久 10000、每次消耗 10 点，消耗几率为 10/10000 = 0.001。
- 消耗几率 = 0：永不消耗，作为建厂初始成本（CapEx），不参与物料流转。

稳态计算中 effective_amount = amount × 消耗几率。消耗几率为 0 的资源在编译时剔除出矩阵。

## 5. 标识符与命名

### 5.1 category:id 格式

资源标识符格式为 `category:id`。`item:water` 与 `fluid:water` 是不同的资源——系统将同名不同类视为独立实体。

- **类别（Category）**：资源标识符前缀，提供默认单位与视觉标识（颜色）。
- **单位（Unit）**：类别在具体模组环境下的默认度量单位。同一类别在不同模组可对应不同单位。
- **基准（Time Base）**：数值的时间参照系。基准是使用方式，非类别固有属性。类别提供偏好基准作为默认建议。

### 5.2 类别注册表

| 类别 | 默认单位 | 偏好基准 | 颜色标识 |
|---|---|---|---|
| `item` | pcs | `/秒` | 灰色调 |
| `fluid` | L | `/秒` | 蓝色调 |
| `energy` | J | `/tick` | 黄色调 |
| `stress` | N·m | `/秒` | 紫色调 |
| `heat` | K | `/tick` | 红色调 |

偏好基准仅在新建物品行时自动填入，不影响已有行的设定。类别条目随模组环境自由增减。

### 5.3 资源覆盖表

仅记录偏离类别默认单位的资产：

| 资产 ID | 类别 | 覆盖单位 |
|---|---|---|
| `mod_power` | `energy` | `EU` |
| `rf_power` | `energy` | `RF` |
| `mech_power` | `stress` | `RPM` |

### 5.4 解析回退链

UI 确定资源显示单位时按三级顺序查找：

| 层级 | 来源 | 优先级 |
|---|---|---|
| Tier 1 | 资源覆盖表显式声明 | 最高 |
| Tier 2 | 类别注册表默认单位 | 中 |
| Tier 3 | 原始 ID 回退 | 最低 |

基准不由解析链决定——每个物品实例自行携带基准值。新建物品行时从类别读取 `preferred_time_base` 作为初始值，用户可后续调整。

## 6. 资源生命周期：四阶段不可逆流转

资源数字身份从用户配置到矩阵求解经历四个严格阶段，不允许越级操作。

```
┌────────────────────────────────────────────────────────────────────────┐
│  阶段一 (定义层)       阶段二 (管线)      阶段三 (视图)    阶段四 (传输)   │
│                                                                        │
│  Recipe IO ──┐                       recipe_inputs  ──┐                │
│              ├──→ [修饰器管线] →      recipe_outputs   │                │
│  Utility IO ─┘     归一化为 Rate      utility_inputs   ├──→ 拍平 → 后端  │
│                                     utility_outputs ──┘                │
│                                                                        │
│    语义隔离              语义消失           语义回归         语义作废     │
└────────────────────────────────────────────────────────────────────────┘
```

### 6.1 阶段一：定义层——严格隔离

两类输入源作为独立数组存储，禁止提前合并：

| 数据源 | 来源 | 语义 | 示例 |
|---|---|---|---|
| 配方 IO（Recipe IO） | 用户填写的配方数据 | "把铁锭烧成钢锭" | `item:iron_ingot` → amount: 1 |
| 设施 IO（Utility IO） | 机器底盘原型的 `fixed_utilities` | "机器需通电运转" | `energy:mod_power` → amount: 32，带 `io_type` |

### 6.2 阶段二：计算管线——统一降维

修饰器管线接收两个独立数组，内部统一处理，将所有离散量纲化数字归一化为每秒速率（Rate/s）。24000 J（一次配方）与 32 J/t（设施持续消耗）归一化后处于同一量纲空间。

### 6.3 阶段三：视图层——结构化拆分

管线产出结果按四数组拆分：

| 数组 | 内容 | UI 用途 |
|---|---|---|
| `recipe_inputs` | 经管线变换后的配方输入（Rate/s） | 节点卡片上半部——加工区 |
| `recipe_outputs` | 经管线变换后的配方输出（Rate/s） | 节点卡片上半部——加工区 |
| `utility_inputs` | 经管线变换后的设施输入 | 节点卡片下半部——基建区 |
| `utility_outputs` | 经管线变换后的设施产出 | 节点卡片下半部——基建区 |

### 6.4 阶段四：传输层——降维拍平

在发起后端请求前，将所有 Input 数组拍平为一个 `Dict[string, number]`，所有 Output 数组拍平为一个 `Dict[string, number]`。同一物质 ID 的多个来源在此求和合并。

| 阶段 | 核心操作 | 语义状态 | 禁止事项 |
|---|---|---|---|
| 定义层 | 原始数据分离存储 | 配方 ≠ 设施 | 禁止提前合并 |
| 计算管线 | 归一化为 Rate/s，执行修饰器 | 全量纲消失 | 禁止保留离散单位 |
| 视图层 | 结构化拆分为四数组 | 语义回归 | 禁止在此层做数值变形 |
| 传输层 | 拍平为 `Dict[id, rate]` | 语义作废，只剩正负 | 禁止保留任何 UI 状态 |

## 7. 修饰器管线

### 7.1 状态对象

```typescript
interface PipelineContext {
  recipeInputs:  Resource[]
  recipeOutputs: Resource[]
  utilityInputs: Resource[]
  utilityOutputs: Resource[]
  durationSeconds: number
  machineStopped: boolean
}
```

管线从深拷贝的原始配方数据初始化 `PipelineContext`。每一步修饰器的 `evaluate()` 接收当前 Context 快照（已由前面所有工序修改后），修饰器直接在 Context 上原地修改。

### 7.2 执行规则

修饰器严格按 `active_modifiers` 数组的索引顺序逐一执行。数组顺序等同于 UI 列表自上而下的顺序。用户可通过拖拽重排顺序。

```
active_modifiers = [M1,      M2,      M3,    ...,    Mn]
                     │       │        │               │
                     ▼       ▼        ▼               ▼
PipelineContext → [ M1 ] → [ M2 ] → [ M3 ] → ... → [ Mn ] → 归一化 → 矩阵
                   原地修改  原地修改  原地修改        原地修改
```

执行流程：

| 步骤 | 操作 | 说明 |
|---|---|---|
| Step 1 | 初始化 | 深拷贝原始配方数据，按 `is_utility` 标志隔离为四个独立数组，创建 `PipelineContext` |
| Step 2 | 遍历修饰器 | 按 `active_modifiers` 顺序逐一调用 `evaluate(ctx, uiState)`，将返回的 `ModifierEffect` 施加到 Context |
| Step 3 | 归一化 | 对所有资源执行 `normalizeRate()`：根据各端口的 `measure_mode` 将 `amount` 转换为 Rate/s |
| Step 4 | 结构化输出 | 产出 `ComputedNodePayload`，四维独立数组保持拆分 |

### 7.3 修饰器接口

```typescript
interface IMachineModifier {
  id: string
  name: string
  compatible_archetypes?: string[]
  ui_schema?: ModifierUISchema[]
  evaluate(
    inputs: Resource[],
    outputs: Resource[],
    durationSeconds: number,
    uiState: Record<string, unknown>
  ): ModifierEffect
}
```

接口不含执行顺序字段——顺序由 `active_modifiers` 数组索引位置决定。新增修饰器只需实现此接口并注册到 `modifierRegistry`，无需修改管线核心。

内置修饰器：

| 修饰器 ID | 类型 | 功能 |
|---|---|---|
| `base_chassis_efficiency` | 引擎内置（通用） | 机器底座效率系数——对 duration 和 IO 数组施加线性乘数 |
| `chance_output` | 引擎内置（通用） | 概率副产物期望值缩放 |
| （模组自定义） | 可插拔扩展 | 模组通过实现 `IMachineModifier` 注入特定逻辑 |

### 7.4 measure_mode 归一化规则

管线末尾的 `normalizeRate()` 函数根据端口 `measure_mode` 将 `amount` 转换为 Rate/s：

| `measure_mode` | 归化公式 | 受 duration 缩放影响 |
|---|---|---|
| `per_cycle` | `amount / duration` | 是 |
| `rate_per_tick` | `amount × 20` | 否 |
| `rate_per_sec` | `amount × 1` | 否 |

`per_cycle` 对应配方原料/产物——配方跑得快，每秒吞吐量自然高。`rate_per_tick` 对应持续效用（J/t）——消耗本质按 tick 计量。`rate_per_sec` 对应固定消耗（如冷却介质）。

### 7.5 并行与超频的顺序依赖

并行修饰器从用户配置的功率容量计算最大并行次数（floor(功率容量 / 单配方基础消耗)），等比放大四数组。超频修饰器读取并行后的 utility 实际值，迭代判断功率阈值，逐级升压加速并限幅钳位。

示例：功率容量 512 J/t，基础配方耗能 24 J/t：

```
并行处理器读取基础值 24 → floor(512/24) = 21 → utility[energy].amount = 504
超频处理器读取 504 → while(504 × 4 ≤ 512) → 否 → 不超频
```

若将并行与超频合并为单个修饰器，两者共享的是同一基础值 24 而非 504，超频判断会得出错误结论。

### 7.6 IO 列表动态变化

修饰器 `evaluate()` 可直接原地增删 Context 中的 IO 数组条目。若模组配方在特定加速档位下新增副产物或移除输入项，由修饰器在 `evaluate()` 内完成，不需要引擎做"编译时配方列分支"。管线将修改后的数组直接归一化并送入矩阵。

## 8. 拓扑编译

### 8.1 Net 隔离

基于边（Edge）的并查集（Union-Find）连通分量检测：

```
对于每条物理连线 (sourceHandle → targetHandle):
  将 source-port-key 与 target-port-key 联合 (Union)

遍历所有节点的所有端口:
  若端口在连线中出现 → 分配 Net_<资源ID>_<短哈希>
  若端口标记为 global 路由 → 分配 Global_<资源ID>
  若端口无任何连线 → 分配 Void_<节点ID>_<资源ID>
```

三种 Net 类型：

| Net 类型 | 命名格式 | 矩阵行为 |
|---|---|---|
| Wired Net | `Net_<id>_<hash>` | 同 Net 端口视为共享同一物流通道 |
| Global Bus | `Global_<id>` | 同一物质 ID 的 global 端口自动聚合为独立虚拟源/汇 |
| Void | `Void_<nodeId>_<id>` | 孤立端口，后端忽略（视为对空排放） |

### 8.2 路由模式

| 路由模式 | 语义 | 编译处理 |
|---|---|---|
| `wired` | 物理拓扑连线 | 并查集检测连通分量，分配 Net 标识 |
| `global` | 全局隐式共享网络 | 同一物质 ID 的 global 端口自动聚合，生成虚拟 Source/Target |

Global 路由以完整物质标识符（如 `energy:mod_power`）为键，不同物质各自拥有独立总线。

### 8.3 Source / Target / Spill 约束注入

**Source 节点**：
- 化学计量矩阵中占一列，列系数 +1.0（向系统注入）。
- 上界由模式决定：`infinite` → +∞，`limit` → `amount`。
- 求解后取整，负值钳位为 0。

**Target 节点**：
- 化学计量矩阵中占一列，列系数 −1.0（从系统取出）。
- 下界由需求量决定：0 即无硬性需求，正数即至少满足此速率。
- Target 与上游端口的连线被前端纳入连通性扫描，使此物品进入等式约束列表。

**内部网络溢流列**：
- 未被 Target 引用的物品自动分配溢流松弛变量 v_k。
- 列系数 −1.0（消纳过剩产出）。
- 目标惩罚系数由动态大 M 机制计算。

### 8.4 LP 模型假设边界

| 假设 | 声明 | 边界外处理 |
|---|---|---|
| 稳态 | 所有变量独立于时间，不模拟瞬态 | 带启动条件的循环由前端注入最小机器数下界或等效 CapEx 约束 |
| 无缓存上限 | 物品可无限囤积于隐式缓冲区 | 缓存上限场景由前端注入额外"溢出消纳 Target"或产能上限 |
| 列系数固定 | 配方列对每物品净速率在求解期内为常数 | IO 列表增减由修饰器在 `evaluate()` 中原地完成 |
| 线性独立 | 配方列间无乘积交叉项 | 邻接加成类机制在编译前结算为等效系数 |
| 无最小启动量 | 机器数可为任意非负实数（求解后取整） | 热循环场景由前端在变量边界中注入最小下界 |

## 9. 线性规划矩阵模型

### 9.1 化学计量矩阵定义

**约定**：列 = 加工变量，行 = 物品 ID。产出取正号（+），消耗取负号（−）。

记 R = 配方数，S = Source 数，T = Target 数，K = 内部网络数，M = 物品全集数量。

**统一变量向量**：

$$
\mathbf{x} = \begin{bmatrix} x_0 & \dots & x_{R-1} & | & x_R & \dots & x_{R+S-1} & | & x_{R+S} & \dots & x_{R+S+T-1} & | & v_0 & \dots & v_{K-1} \end{bmatrix}^\top
$$

| 变量段 | 物理意义 | 约束范围 |
|---|---|---|
| x₀…x_{R-1} | 每个配方的机器台数（可小数） | [0, upper_i] |
| x_R…x_{R+S-1} | 每个 Source 节点的实际吞吐速率 | [0, cap_i] |
| x_{R+S}… | 每个 Target 节点的实际吞吐速率 | 由权重与需求量决定 |
| v₀…v_{K-1} | 每个内部网络的溢流松弛量 | [0, +∞) |

**化学计量矩阵 A ∈ ℝ^{M × (R+S+T+K)}**：

- 配方列：配方 j 产出物品 i（速率 v）→ A_{i,j} = +v；消耗 → A_{i,j} = −v。
- Source 列：A_{i, R+s} = +1.0。
- Target 列：A_{i, R+S+t} = −1.0。
- 溢流列：A_{i, R+S+T+k} = −1.0。

### 9.2 约束体系

#### 9.2.1 溢流约束

对所有非 Void 物品 i，若存在正净产出（有配方产出），引入非负溢流松弛变量 v_k：

$$
\sum_{j=0}^{R+S+T-1} \mathbf{A}_{i,j} \cdot x_j - v_k = 0
$$

v_k = 0 表示物品完全平衡；v_k > 0 表示存在净过剩产出。约束始终可行——v_k 以变量形式吸收供需差额。

#### 9.2.2 Target 需求的边界约束

Target 节点的需求量不通过等式约束实现，而是通过变量下界（Bounds）：

| Target 模式 | 变量下界 | 目标系数 | 语义 |
|---|---|---|---|
| Demand | 用户指定需求量 d | 0 | 下界锁定吞吐量 |
| Maximize | 0 | −10,000 | 驱动求解器最大化吞吐 |
| Overflow | 0 | +0.001 | 抑制不必要溢流排放 |

Sink 变量在物品行中系数为 −1.0。x_{R+S+t} ≥ d 等价于系统至少从此路径取出 d 单位/秒。

#### 9.2.3 约束选择逻辑

```
对每个物品 i:
  if 物品 i 是 Void_ 前缀:
    → 跳过约束
  else if 物品 i 的行存在正系数（有配方产出）:
    → 施加溢流约束: A_i · x - v_k = 0
  else:
    → 跳过约束（纯消耗品/中间产物为零，视为隐式无限供给）
```

### 9.3 阶梯式权重与目标函数

#### 9.3.1 预设权重

| 角色 | 系数值 | 物理语义 |
|---|---|---|
| Maximize（最大化产出） | −10,000 | 驱动求解器最大化此 Target 吞吐 |
| Demand / Overflow | 0 | 中性流向，不施加推拉 |
| Recipe（机器运行成本） | +1 | 每个配方变量贡献 +1 成本，引导最少机器数 |
| Minimize（最小化副产物） | +100 | 引导低副产物工艺路线 |
| Spill v_k（溢流松弛） | 动态大 M | 物理阻塞为最高代价选项 |

权重值之间保持 100× 量级差（1 : 100 : 10,000）。

#### 9.3.2 标准形式

$$
\begin{aligned}
\min \quad & \mathbf{c}^\top \mathbf{x} = \sum_{j=0}^{R-1} c_j^{\text{recipe}} x_j + \sum_{t=0}^{T-1} c_t^{\text{target}} x_{R+S+t} + \sum_{k=0}^{K-1} c_k^{\text{spill}} v_k \\
\text{s.t.} \quad & \mathbf{A}_{\text{ub}} \mathbf{x} \leq \mathbf{b}_{\text{ub}} \\
& \mathbf{A}_{\text{eq}} \mathbf{x} = \mathbf{b}_{\text{eq}} \\
& \mathbf{0} \leq \mathbf{x} \leq \mathbf{u}
\end{aligned}
$$

Source 变量系数恒为 0（外生输入不计入优化目标）。

#### 9.3.3 配置模式速查

| 模式 | 权重 | 需求量 | 效果 |
|---|---|---|---|
| Maximize | −10,000 | 0 | 全部可用产能投喂此 Target |
| Demand | 0 | 用户指定 | 恰好满足需求量 |
| Overflow | 0 | 0 | 来多少接多少，作为物料出口 |
| Minimize | +100 | 0 | 压低此 Target 吞吐，倾向不产生此物质的工艺 |

#### 9.3.4 动态大 M

v_k 的目标系数在后端组装矩阵前动态计算：

$$
c_k^{\text{spill}} = \max\left(1{,}000{,}000,\; \max\left(\left| c_{\text{user}} \right|\right) \times 10\right)
$$

其中 max(|c_user|) 为当前求解任务中所有用户可配置权重的最大绝对值。保底下界 1,000,000。此公式确保溢流惩罚在数量级上始终比任意用户配置权重高 10 倍。

### 9.4 变量边界

| 变量类型 | 模式 | 下界 | 上界 |
|---|---|---|---|
| Recipe | auto | 0 | +∞ |
| Recipe | limit | 0 | manual_machines（手动上限） |
| Source | infinite | 0 | +∞ |
| Source | limit | 0 | amount（有限供给） |
| Target | — | demand（用户指定） | +∞ |
| Spill | — | 0 | +∞ |

### 9.5 求解与结果回代

使用 `scipy.optimize.linprog`（highs 方法）求解。求解完成后执行全量矩阵回代：

$$
\mathbf{r}_{\text{net}} = \mathbf{A}_{\text{full}} \cdot \mathbf{x}^*
$$

A_full ∈ ℝ^{M × (R+S+T+K)} 为完整化学计量矩阵（含溢流列）。回代结果按正/负拆分：

- r_net[i] > 0 → 入 `system_outputs`
- r_net[i] < 0 → 取绝对值入 `system_inputs`

配方变量结果按 `Math.ceil(x_i − ε)` 向上取整为整数机器数，利用率 = exact / actual。

| 求解状态 | 含义 | 前端反馈 |
|---|---|---|
| success | 找到最优解 | 展示完整结果 |
| infeasible | 硬约束冲突 | 提示检查供需矛盾 |
| unbounded | 存在负权重 Target 但缺乏物理瓶颈 | 提示为上游设定产能上限 |

### 9.6 CapEx / OpEx 分离

| 概念 | 内容 | 数学处理 |
|---|---|---|
| OpEx（运营成本） | 每秒消耗的物质与能量 | 进入稳态矩阵，作为变量系数或约束 |
| CapEx（建厂成本） | 机器造价、消耗几率为 0 的物品 | 不进矩阵，前端编译时剔除，汇总为一次性 BOM |

消耗几率为 0 的资源在归一化时 effective_amount = 0，在 `flattenForBackend` 中被过滤。

## 10. 节点图编辑器（前端）

### 10.1 节点类型

前端基于 React Flow 构建，支持四种节点类型：

| 节点类型 | 标识 | 功能 |
|---|---|---|
| SourceNode | 绿色输入源 | 定义外生输入（无限矿、有限供给） |
| RecipeNode | 蓝色加工节点 | 定义物质转换配方（输入 → 机器 → 输出） |
| TargetNode | 橙色目标节点 | 定义最终需求，可配置需求量与权重 |
| SplitterNode | 紫色分流器 | 将单种物品流量按比例分配至多个下游 |

状态管理：画布状态由 React Flow 的 `useNodesState` / `useEdgesState` 接管，结合 Zustand 实现资源注册表细粒度订阅——组件仅在所引用的资源类别变化时重渲染。

### 10.2 基建区与加工区的 UI 映射

Recipe 节点的编辑面板呈现两个语义区域，直接映射第 4.2 节的基建/加工划分：

| UI 区域 | 数据来源 | 编辑权限 |
|---|---|---|
| 上半部：加工区（Recipe IO） | 配方定义 | 用户可编辑（配比、概率、催化剂标记） |
| 下半部：基建区（Utility IO） | 底盘原型 | 根据 Archetype 的 `amount_mutable` 属性决定是否可编辑 |

消耗几率为 0 的资源在加工区中以灰色显示并附带非消耗标记。

### 10.3 SystemHUD

SystemHUD 遍历求解返回的 `system_inputs` 和 `system_outputs`，按类别聚合展示全局物流摘要：

- 按类别（item / fluid / energy）分组展示系统级净输入/净输出。
- 借助 `category:asset` 字典解析每条物流的单位与颜色。
- 高亮瓶颈资源——净消耗速率接近系统总供给上限的物品。
- 展示全局电力总消耗与总供给差值。

### 10.4 分流器节点

#### 10.4.1 定义

分流器节点（SplitterNode）是一种独立节点类型，与 Recipe 节点同构但语义专一：

| 属性 | 说明 |
|---|---|
| 输入端口 | 单一输入端口，接收一种物品 |
| 输出端口 | 2 至 N 个输出端口，各配置分配比例（ratio），所有比例之和为 1.0 |
| 吞吐变量 | 分流器作为一个 LP 变量 x，表示通过此分流器的总流速 |

#### 10.4.2 矩阵编译

分流器在化学计量矩阵中占一列，每个分流器对应一个 LP 变量 x_k：

- 输入行：A_{i,in} = −1.0（消耗上游物品 i）
- 输出行 j：A_{i,out_j} = +ratio_j（以比例 ratio_j 产生物品 i，流入下游 Net）

此节点不改变物品物理身份，其作用为强制约束下游消费的比例关系。

#### 10.4.3 与 Target 权重的协同

分流器在"物品分流"层面控制（同种物品流向不同消费链的比例）；Target 权重在"需求激励"层面控制（求解器对特定 Target 的偏好程度）。两者可协同：分流器按 40:60 分配铁板，下游两个 Target 各自以不同权重驱动求解器行为。

## 11. 扩展机制

### 11.1 模组插件架构

核心引擎不含任何硬编码游戏逻辑。所有模组特定行为通过三个可插拔扩展点注入：

| 扩展点 | 机制 | 示例 |
|---|---|---|
| 资源覆盖表 | `ResourceOverrideTable` 中声明模组特定资产的单位覆盖与类别归属 | `mod_power` → unit: `EU` |
| 机器底盘原型 | 定义模组特定机器的 `fixed_utilities`、默认修饰器 | 电力机器：`fixed_utilities: { energy:mod_power }` |
| 修饰器 | 实现 `IMachineModifier` 接口，注入模组特定物理仿真逻辑 | 并行处理器：功率容量 → 最大并行次数 → 四数组等比放大 |

新增模组支持只需配置这三个扩展点。核心管线与矩阵求解器无需代码改动。

### 11.2 多语言本地化（i18n）

本地化采用三级级联架构，与资源解析回退链（5.4 节）同构：

| 级别 | 内容 | 优先级 |
|---|---|---|
| Tier 1：资源显式翻译 | 特定资产 ID 的专门译名 | 最高 |
| Tier 2：类别默认翻译 | 类别级别的通用显示名 | 中 |
| Tier 3：原 ID 回退 | 未翻译时直接显示 ID 原文 | 最低 |

### 11.3 CapEx 物料清单（BOM）

消耗几率为 0 的资源排除在稳态矩阵外。前端提供 CapEx BOM 面板，汇总以下一次性建厂清单：

- 所有配方节点的消耗几率为 0 的物品。
- 所有 Source 节点的机器造价（若已录入）。
- 所有 Recipe 节点的机器造价（若已录入）。

CapEx BOM 独立于 OpEx 运营矩阵，实现建厂与运营的彻底分离。
