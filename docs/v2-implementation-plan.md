# OmniFlow v2：可独立评审的实施拆分

状态：PR-01–05 已完成；PR-06–12 已在当前工作区完成实现、自动化回归及所列界面和性能核验（2026-10-23）。正式计算入口现使用显式网络编译器和版本化稀疏 LP，旧业务节点求解路径已删除。阶段编号指实施计划，尚未创建远程 PR；完成证据与未完成项见 [本轮验证记录](validation/v2-completion/README.md)。

依据：[AGENTS.md](../AGENTS.md)、[v2 设计](technical-design-v2-proposal.md)、[代码差距评估](v2-code-gap-assessment.md)。T01–T24 指 v2 设计中的验收案例。

## 1. 拆分原则与交付边界

- 每个改动只回答一个主要评审问题，包含对应实现、必要测试、契约与迁移说明。
- “可独立评审”不等于没有依赖。依赖项合并后，本改动必须可构建、可验证；不得将编译失败留给后续 PR。
- 单位、端口、编译 IR、求解器分别由自然的领域模块负责。不得为了缩小 diff 再造临时字段、双写状态或条件分支。
- 基础模块可先作为真实测试覆盖的领域能力合并；正式计算入口在 PR-07 一次性切换，避免用户用到半套新守恒规则。
- 文件范围是预计主要落点，实施时根据调用链核实；不顺手修复无关 lint、样式或重构问题。
- 保留工作区已有改动。开始实施时记录检查基线，只提交本批次相关内容。
- 本计划不包含 MILP、库存时序、边级物流容量、自动选择工况。

## 3. 每个改动的具体范围

### PR-01：当前 API 的可靠性与回归基线

**评审问题：无效模型能否明确失败，合法返回值能否被前端准确消费？**

- 修改 `backend/main.py`、`src/common/types/api.ts`、`features/calculation/capEx.ts` 及相关调用方。
- 统一 `machines_actual`；非法节点、非法模式和非有限数值返回结构化错误，停止“记录日志后跳过”。按实际 status 区分不可行、无界、限制和求解器错误。
- 建立最小测试入口：前端拟采用 Vitest，后端 pytest；实施时核对现有工具兼容性并锁定依赖。不增加整套浏览器测试基础设施。
- 六个已复现案例进入测试目录：本 PR 修复的行为断言为通过；其余已知问题标注为待实现的验收案例，不把错误行为写成长期 golden output，也不让主分支长期红灯。
- 文档记录真实测试命令、Python 依赖安装方式；更新 AGENTS 的“尚无 runner”说明。

**验收：** 非法 Source 不再得到空 success；需求 1.2 台且每台一件催化剂时 BOM 按 2 件计算；Source 0.25/s 保留小数（T15、T23 的相关部分）。

**不包含：** 改目标函数、守恒或新 LP API。这里是现有契约的局部修复，不用临时重写一份 v2 求解器。

### PR-02：可组合单位表达式、环境与持久化

**评审问题：单位能否像数学表达式一样组合，并让同一物理量在运算、显示与存档恢复后保持一致？**

本节采用用户确认的单位表达式方案，替代前期文档中“单一 unitId + 独立时间换算分支”的接口设想。借鉴单位代数，不要求实现 Mathematica 的完整功能。

#### 模型与职责

- 新建 `src/common/units/`，同步登记 ESLint 模块边界。`UnitRegistry` 注册原子单位、尺度前缀、派生关系和允许的转换；`Unit` 表达不可变的单位乘积、商与整数次幂；`Quantity` 保存数值和单位，提供运算与转换。
- `UnitSystem` 作为统一入口，组合注册表与显式环境快照。上述职责不重复实现换算；类内部不读取 Zustand。
- 尺度前缀与无前缀基本单位分别注册。例如 `kg = kilo(g)`，不将 kg 和 g 注册成两个互不相关的单位。“基本单位”指本系统选定的原子单位，不要求等同于 SI 基本单位。
- 输入/显示表达式保留 `{ baseUnitId, prefixId }` 等结构化信息；不通过任意截取单位字符串识别前缀。显示符号 `m` 与前缀 `milli` 由不同身份区分，`mB` 的含义须由游戏注册表声明。
- 对可乘除的单位，展开已注册派生关系后，归一化为“倍率 + 原子单位指数表”：`kg → 1000 × {g: 1}`、`m/s → {m: 1, s: -1}`、`m/s² → {m: 1, s: -2}`。约去零指数，统一排序；倍率合并，不能重复应用前缀。
- 加减和转换要求归一化单位兼容；乘除合并指数。仅显式注册的关系可以连接不同原子单位，不能仅凭显示类别相同就换算。

拟议调用方式（不是已实现的源码）：

```ts
const speed = Quantity.of(10, units.m.divide(units.s))
const duration = Quantity.of(3, units.s)
speed.multiply(duration).to(units.m) // 30 m

Quantity.of(1, units.g.withPrefix('k')).to(units.g) // 1000 g
units.m.divide(units.s.pow(2)) // m/s²
```

#### 时间与资源语义

- `tick` 是环境相关的时间单位：20 TPS 时注册环境关系 `tick = 0.05 s`。`kEU/tick` 直接由带前缀的 EU 除以 tick 构成，不再另行维护一套速率换算算法。
- `cycle` 属于配方语义，不注册为全局固定时间单位。每周期用量 2 L、当前周期 4 s，由配方层计算 `Quantity(2, L) / Quantity(4, s)`；修饰器改变周期后重新求值。
- 原有 `per_cycle`、`rate_per_tick`、`rate_per_sec` 可作为编辑意图/迁移输入，由单一适配入口生成单位表达式。表达式生成后不可再次按 time_base 缩放；例如 W 已是 J/s，不能再除一次秒。
- Quantity 的单位代数不改变 `resourceId`；铁与铜不得相加为同一物流资源，EU/RF 不默认互换。资源身份校验由领域层负责，单位类只保证数量换算。
- 概率、损耗和配方资格仍由管线处理。带偏移的绝对温度不能套用倍率乘除；本 PR 不支持的仿射单位运算明确报错，未来支持时须区分温度和温差。

#### 接入与存档

- 接入 `registry.units.ts`、资源注册表、`common/utils/time.ts`、`rateFormat.ts`、`normalizeRate`、Source/Target 编辑与项目设置，所有调用方委托同一单位运算实现。
- UI 第一版使用单位选择与结构化表达式，格式化生成 `kg`、`m/s` 等标签；不增加自由文本解析器、通用符号求解或分数次幂系统。
- 每次编译使用同一环境快照；TPS、前缀或单位定义改变时相关缓存失效。仅改变显示前缀不改变标准数值，不触发物理模型重算。
- 保留计算精度，显示时再舍入；校验有限数值、除零、周期、TPS、未知单位和派生定义循环。移除零周期的 1e9 兜底；GT tick 下限由插件依据环境决定。
- 保存数值、结构化单位表达式、注册定义和 TPS，不保存类实例；派生的归一化结果只做可失效缓存。恢复后构造运行时对象，不能依赖 JSON 恢复原型。

**验收：** 在 T10、T23 的基础上增加以下案例：

| 案例 | 预期 |
|---|---|
| 1 kg 转 g；1 kg + 500 g | 1000 g；1.5 kg |
| 10 m/s × 3 s；m/s² × s | 30 m；m/s |
| 1 kg + 1 s，或缺少注册关系的单位转换 | 明确报错 |
| 32 EU/tick，TPS 从 20 改为 40 | 提交速率从 640 变为 1280 EU/s，无旧缓存 |
| 2 L/周期，周期 4 s；显示为 mL/s | 0.5 L/s；500 mL/s，物理模型不变 |
| 已声明 W = J/s，输入 1 kW | 1000 J/s，不重复除以秒 |
| 带偏移绝对温度参与普通单位乘除 | 明确拒绝，不按线性倍率处理 |
| 未知前缀、非法 TPS、零周期、循环派生定义 | 明确失败，不猜测或静默回退 |
| 导出/导入 kg、m/s、EU/tick 与环境定义 | 表达式与物理量均保持一致 |

**迁移：** 为单位表达式与环境快照升级文件版本。旧标签只按已注册的明确映射迁移，不自动拆解任意字符串；未知标签保留为独立原子单位、使用无前缀身份。旧文件缺环境时提示采用的默认值。文件版号与“技术设计 v2”各自独立。

### PR-03：稳定端口身份

**评审问题：端口身份能否在同名、重排、复制与持久化后保持正确？**

- 修改 Resource/Recipe/Endpoint 类型与 schema、编辑器、React Flow handle、连接校验、复制粘贴、拓扑和存档迁移。
- 将 resourceId 与持久 portId 分开。连线使用 portId 定位，再查询资源兼容性；不得继续用“两个 handle 字符串相等”作为资源校验。
- 先按独立端口查找 Net，再聚合系数。`_uid` 只有在验证唯一性与稳定性后才可复用，不能无条件照搬。
- 复制节点时重建身份并映射选中子图内部连线；重排不改变身份；删除端口产生明确的失效边状态。
- 所有现有调用方随该 PR 完成迁移，避免留下两种 handle 含义。

**验收：** 同机加工水/冷却水分别连接两个 Source；同资源输入输出不误合并；重排、复制、撤销、保存再读不串线。验证 T07、T08、T22 的身份部分。

**迁移：** 如需进一步改变文件结构，再升级文件版本，不强行复用上一版本。旧边唯一可解析则自动迁移，多候选时保留数据并定位待修复端口，不猜测连接。

### PR-04：确定性修饰器与最终端口

**评审问题：相同配方和环境能否生成相同的、可解释的最终计算输入？**

- 修改 `modifier.types.ts`、管线、内置修饰器与插件、配方缓存和必要的预览 UI。
- 按 v2 统一为只读 Context → Effect，由管线一次应用；Effect 仅包含当前插件确实需要的变换、端口变化和说明，不设计通用脚本语言。
- 输出 final ports、资格/停机原因、实际并行配置、BOM 占用与步骤轨迹。动态端口具有确定 ID。
- 校验执行依赖；区分每周期、每并行槽、每运行机器和每安装机器的缩放依据。停机状态不得被简单的“输出全零”替代。
- 缓存包含配方、环境、单位与插件版本；不静默过滤未知修饰器或自定义类别。

**验收：** 并行影响后续超频；非法重排被拒绝；动态新增/删除 IO 可定位；耗能但不产普通物料的合法设施不会被统一挡住；相同快照计算结果稳定（T11）。

**迁移风险：** 自定义插件接口变化须同步版本与提示。现有算法尽量保留，只迁移职责和输入输出契约。

### PR-05：通用稀疏 LP 求解模块

**评审问题：给定标准数学模型，后端是否正确求解并诚实报告状态？**

- 从单文件路由中分离 `backend/solver/` 与请求/响应 schema；同步 TypeScript 契约和跨语言模型 fixtures。
- 支持稀疏等式/不等式、边界、按优先级分层目标、统一时间预算和逐层容差。求解器不识别 Recipe/Source/Target。
- 校验非有限值、索引、重复 ID、界限、模型规模；重复系数按已定义规则相加。逐层验证残差与边界，超时只返回已验证的可行方案。
- 不使用大 M 优先级，不引入巨大隐含变量上界；不构建稠密中间矩阵。
- 此阶段通过函数级测试调用新模块，不增加第二个面向用户的计算入口。当前路由保持旧逻辑，PR-07 整体替换。

**验收：** 慢配方目标仍优先最大化；无界、不可行、超时、错误正确区分；分层目标不会因显示单位变化而变更；矩阵重复项与小数变量正确（T09、T16、T21、T23）。

### PR-06：严格网络编译与显式边界

**评审问题：图上的每项资源和假设是否都进入了正确的守恒/容量约束？**

- 重构 `features/calculation/topology.ts`、`payloadBuilder.ts`，按实际职责形成编译 IR、模型构造与来源映射模块，不按文件大小机械拆分。
- 以最终端口构图；使用确定性的 Net 身份；Global 按 scope/resource/bus 聚合且不提供隐式供应。
- 定义显式 Source、产品交付、允许排放、禁排、固定容量、固定负荷与目标配置的 schema；边界/目标编辑器与数据定义一起交付。
- 目标支持至少、恰好、最大化及明确优先级；同级多目标选择归一化权重或固定配比，不凭节点顺序分配优先级。
- 每个内部 flow Net 建立守恒，缺少正流量输入时阻止编译；封闭输出保留约束。capacity 用不等式，state 在固定工况校验。
- 保留端口毛流量、行列来源；正式计算入口尚不使用新结果。新配置不应被旧求解器默默消费：PR-07 前不开放这些新编辑入口。

**验收：** 通过编译器 + PR-05 求解器的集成 fixtures 验证 T01–T05、T07–T11、T17、T18、T22。固定基建负荷正确进入模型，自动安装不支持的负荷明确拒绝精确求解。

**为什么不能只补 if：** 漏接线、Global、同机双水路与排放共用网络语义；必须由统一 IR 和守恒编译拥有，而不是四处补例外。

### PR-07：正式入口切换与可信结果

**评审问题：用户从编辑到结果是否完整使用同一版模型？**

- 修改 `/api/calculate`、debug 路由、`useCalculation`、canvas store、Source/Target/Recipe 结果映射与 SystemHUD。
- 正式路由委托 PR-05，新前端发送 PR-06 的 LP；同一 PR 删除旧业务节点建模、Void 跳过、自动 Spill、大 M 及 debug 的重复构建逻辑。
- 请求携带 schema version、request id、document/model revision 与编译指纹；响应运行时校验并拒绝旧版本回写。编辑后标记结果过期。
- 摘要分别来自 Source/Target/Spill 变量；守恒回代只用于残差。按 Net 展示，再提供资源汇总。
- 开放新边界与目标 UI；错误定位到端口；移除“所有普通产物为零就禁止计算”的粗略规则。
- 旧图使用统一迁移流程展示隐式供给/排放假设，不无声开启新规则，也不为旧文件保留第二套求解语义。

**验收：** 六个历史反例按新预期通过；UI 完整验证 T01–T11、T15–T18、T20–T23 的相关路径；10/s 进出料摘要正确；旧响应不能覆盖新图。

**发布边界：** 这是 API 破坏性变更，前后端必须协调发布。版本不匹配应明确失败。需要回退时整体回退该发布，不能自动降级到旧数学规则。

### PR-08：安装、运行、BOM 与启动

**评审问题：用户拿到的安装清单是否与模型假设一致？**

- 修改结果类型、机器卡片、BOM 与容量/固定负荷配置；明确 operating_equivalent 与 recommended_installed。
- 小数运行量计算物流；安装建议处理数值容差与零利用率。每安装机器固定负荷只在固定安装数下精确建模；自动安装模式明确限制。
- BOM 根据最终工况和安装数，区分每机器、每槽位、全局占用；不计未运行且未固定安装的方案。
- 启动种子、催化剂、预热条件独立显示。循环检测仅指出需确认启动条件，不声称证明动态可启动。

**验收：** T12、T14、T19、T24；Source 吞吐不作为安装台数；已有设备与新增安装建议清楚区分。界面附截图。

### PR-09：结构化诊断与满载解释

**评审问题：不可行时能否告诉用户哪里冲突，而不误导为可运行方案？**

- 新增受限的弹性诊断流程，复用稀疏模型、求解服务和来源映射；前端提供节点/端口定位。
- 只放松允许诊断的约束，按明确尺度惩罚缺口。记录诊断假设，不宣称找到唯一原因或最小冲突集合。
- 区分“达到上限”和“增容有收益”。第一版默认显示余量与满载；收益判断仅在边际信息可解释或完成小幅扰动验证后显示。
- 诊断耗时受预算约束；失败不能覆盖原始 infeasible 状态。

**验收：** T03 显示供给缺口、T04 显示废物出口冲突；诊断方案不能被当作正常安装/物流结果；多个可能冲突有明确措辞。

### PR-10：固定比例分流器

**评审问题：分支分配、堵塞与排放行为是否符合用户看到的比例？**

- 注册 SplitterNode、端口编辑、比例校验、吞吐变量和编译系数。使用现有通用编译与端口体系，不伪装成带特殊字段的 Recipe。
- 不计机器台数成本、不取整。比例总和在容差内规范化；负值与非法和报错。
- 拒绝输入输出同 Net、输出互相合流的退化配置；支路禁排且堵塞时限制整体流量。
- 文案明确保证分配比例，不保证存在外供/旁路时的消费比例。

**验收：** T13；支路显式排放、容量瓶颈、0 比例支路、复制/保存恢复均有案例和 UI 截图。

### PR-11：执行池与运行预算

**评审问题：慢求解或并发请求是否会拖住整个 API？**

- 将同步求解放入有界执行机制；为排队、全部目标层、诊断与可选扰动设置明确预算。
- 设模型大小、并发与线程上限；返回排队/求解/总耗时。对未开始的旧任务取消或淘汰，运行中的任务受求解预算限制。
- 不宣称前端 AbortController 能中止已运行的 Python 求解；若必须强制终止，采用可回收的进程边界并验证资源释放。
- 过载返回明确错误，不允许队列无限增长。

**验收：** 并发长短请求时 API 保持可响应；超时保留正确状态；连续修改不积累无限任务；排队时间计入预算（T20、T21 的运行层补充）。

### PR-12：发布验收、迁移与实测性能

## 4. 统一评审清单

每个 PR 描述只需覆盖与本改动相关的项目：

1. **问题与行为：** 一个具体触发场景及前后差异。
2. **边界：** 哪个模块拥有规则，调用方是否同步更新；不依赖未合并 PR 才能构建。
3. **契约：** 类型、schema、单位、环境、端口、版本是否一致。
4. **验证：** 实际执行命令、结果、关联 T 编号；UI 附截图。
5. **迁移与回退：** 是否破坏存档/API，歧义如何呈现，如何保留原数据。

不设置“每完成一步必须重新请求许可”的流程；在已授权的实施范围内按依赖推进。需要新增产品决策时先给出具体方案及影响，不用通用审批代替工程判断。
